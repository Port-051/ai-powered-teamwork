## 초안 A — `worktree-glimmering-swinging-bee` (커밋 2fdd09b, "Phase 3-1"로 추가됐던 내용)

### 데이터 모델 — 대화에서 "사실 단위"를 구조화해 추출

| 타입 | 예시 | 특징 |
|---|---|---|
| **Decision(결정)** | "배포는 매주 화요일로 통일" | 새 결정이 오면 이전 결정은 `superseded`로 마킹 (덮어쓰기 가능) |
| **Fact(사실)** | "고객사 A는 인보이스를 월말에 끊는다" | 출처(누가/어느 스레드)와 신뢰도 태그 포함 |
| **Todo/Owner(할일)** | "김동연이 배포 스크립트 작성" | 진행/완료 상태 추적 |
| **Know-how(노하우)** | "Mattermost 봇 토큰 재발급은 관리자 콘솔 X 메뉴" | 절차형, 검색 우선순위 높음 |

### 파이프라인

```
멘션(@ai) 또는 지정 채널 메시지
   → LLM이 위 4종 중 해당하는지 분류·추출 (해당 없으면 skip, 비용 절감)
   → 기존 지식과 충돌 검사 (같은 주제 Decision이 있으면 supersede 처리)
   → 지식 저장소에 upsert (구조화 필드 + 임베딩 둘 다)
   → 팀원 질문 시: 구조화 필드로 필터링(최신 Decision 우선) + 임베딩 유사도로 후보 압축 → LLM이 답 생성
```

### 개인 ↔ 팀 브릿지 (권한/비밀 보호)

- 팀 지식 그래프는 팀 채널 단위로 스코프 분리. DM 내용은 팀 지식으로 승격하지 않음.
- Hermes(개인 에이전트)는 팀 지식 그래프를 "외부 도구"처럼 조회만 함(tool-use) — 개인 세션 기억과 팀 지식을 분리.

### 저장소

- MVP: Mattermost DB는 원문 보관용, 구조화 지식은 별도 경량 저장소(예: **SQLite + sqlite-vec** 임베딩)로 시작. Decision의 `superseded` 갱신 같은 구조화 업데이트는 Mattermost DB만으로는 불가능해서 별도 저장소가 필요하다는 논리.

## 초안 B — `worktree-squishy-questing-pine` (커밋 066611a, "Phase 4-1"로 추가됐던 내용)

### 데이터 흐름 3단계

```
[캡처] Mattermost 이벤트 (멘션 응답 / 명시적 등록 커맨드)
   ↓
[추출·정제] 우리 레이어가 "지식 단위(Knowledge Unit)"로 가공
   ↓
[저장·색인] 팀 전용 벡터DB (임베딩 + 구조화 메타데이터)
   ↓
[검색·주입] 다음 @ai 호출 시 관련 지식을 컨텍스트로 불러와 응답에 반영
```

### 지식 단위(Knowledge Unit) taxonomy

- **결정(Decision)** — "우리 이거 A로 하기로 함" (근거·날짜·작성자 포함)
- **사실/노하우(Fact)** — 재사용 가능한 정보 (예: "이 API는 시간당 100회 제한")
- **미해결 이슈(OpenQuestion)** — 아직 답이 안 난 것
- **용어/정의(Glossary)** — 팀 내부에서만 통하는 약어·용어

각 단위는 `출처 스레드 링크 + 채널 + 작성자 + 타임스탬프 + 신뢰도(합의 vs 개인 의견)`를 메타데이터로 가짐.

### MVP 추출 방식: 명시적 등록 우선

- `@ai 이거 기억해` 같은 커맨드로 직접 트리거.
- 스레드 종료 자동 요약·추출은 노이즈·오추출 리스크가 커서 **자동 추출은 MVP 이후**로 미룸.

### 저장소

- 팀 전용 벡터DB를 Mattermost DB와 분리 운영. 검색·구조화가 쉽고 추후 SaaS화·이식성이 좋다는 논리.

### 검증 계획 (Phase 7 확장안)

가설 4개 + 각각 지표·방법·회수 시점을 상세히 제시했었음:

1. **문제 공감** — 인터뷰 5건 중 공감 응답 ≥4/5, 07/09 전 확인
2. **기술 리스크** — 멘션→응답 왕복 지연 ≤5초, 07/09 확인
3. **핵심 novel 가설(등록 기반 Knowledge Unit 재사용)** — 등록률(팀당 주 5건↑) / 재사용률(30%↑) / 신뢰도 태깅 정확도, 07/30·10월 확인
4. **리텐션** — 4주 이상 사용 팀의 WAT 유지율과 누적 Knowledge Unit 수 상관관계, 10월 확인

공통 원칙: 각 가설에 날짜 박힌 회수 시점 + 미달 시 행동(재정의/로드맵 조정)을 명시.

### 부수적으로 들어있던 인프라 개선 (참고용, 별도 검토 필요)

`.claude/hooks/pre-prompt-pull.sh`에서 `git pull` 실패 시 처리를 아래처럼 바꾼 것도 같이 있었음 — PLAN.md와는 무관하지만 훅 안정성 관련이라 참고로 남김:

```diff
-if ! git pull --quiet origin main >/dev/null 2>&1; then
+if ! git pull --rebase --quiet origin main >/dev/null 2>&1; then
+  git rebase --abort >/dev/null 2>&1 || true
   echo '{"systemMessage": "..."}'
   exit 0
 fi
```

`--rebase` + 실패 시 `rebase --abort`로 정리하는 방식이 지금 main의 훅보다 더 안전할 수 있어 보임 — 팀 논의 후 채택 여부 결정.

## 초안 C — 신홍재 5단계 파이프라인 스케치 (2026-07-07, `port_051/decisions.md` 원문)

> PLAN.md Phase 8 8월 재설계용 사전 스케치로 decisions.md에 남겨진 것 — 신홍재가 제안, 아직 PLAN.md 미반영.

### 5단계 파이프라인

```
수집(Ingest) — 멘션 무관 채널 전체·스레드 단위로 수집
   ↓
선별(Filter/Classify) — 저비용 모델로 결정/노하우/사실 vs 잡담 분류
   ↓
추출(Extract) — {유형, 요약, 참여자, 채널, 원본링크, 시각} 구조화
   ↓
저장(Store) — 임베딩 + 벡터DB, 개인/팀공유 권한 태그 (기본값: 팀공유)
   ↓
검색/응답(Retrieve) — 개인 기억 + 팀 공유 저장소를 Hermes에 tool로 노출
```

- **핵심 제안**: "원문 저장 후 RAG 검색"보다 **"실시간 요약·구조화 축적"**을 추천 — 나중에 검색할 때 원문을 다시 해석하지 않고, 미리 구조화해둔 걸 바로 씀.
- **미결정**: (a) 실시간 처리 vs 배치 처리 (b) 권한 태깅 자동 vs 수동.
- 초안 A/B와 차이점: "멘션 무관 채널 전체 수집"이 기본값이라는 점 — A/B는 멘션 또는 명시적 등록이 트리거인데, 초안 C는 채널 전체를 상시 수집 대상으로 봄 (프라이버시 필터의 역할이 더 커짐).

## 초안 D — 김동연의 단순화 MVP 제안 (2026-07-07, `port_051/decisions.md` 원문)

> 지식 단위 분류·임베딩 검색 없이, 훨씬 단순한 방식으로 7월 MVP의 핵심 체험(팀 대화를 참고해 답하기)이 가능하다는 관찰.

- **방식**: 어댑터가 **Mattermost 검색 API**로 관련 메시지를 그때그때 가져와 개인 Hermes 기억과 합쳐 프롬프트에 넣는다. 별도 지식 저장소·임베딩·분류 모델이 필요 없음.
- **권한 처리가 "공짜"로 해결됨**: 사용자 본인의 Mattermost 토큰으로 검색하면, 그 사람이 못 보는 비공개 채널은 애초에 검색 결과에서 자동으로 빠진다 — 별도 권한 태깅 로직을 안 짜도 됨.
- **트레이드오프**: 정교한 지식 단위 분류·임베딩·세밀한 가시성 태그(초안 A/B/C가 하려는 것)는 이 방식엔 없음 — 8~9월 고도화 대상으로 미룸. 즉 초안 D는 "MVP는 최대한 단순하게, 정교한 구조화는 나중에"라는 입장이고, 초안 A/B/C는 "처음부터 구조화된 지식 모델을 만들자"는 입장이라 **방향 자체가 갈림**.
