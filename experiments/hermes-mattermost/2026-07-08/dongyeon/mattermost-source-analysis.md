# Mattermost 서버 소스코드 분석 (dongyeon, 2026-07-08)

GitHub의 `mattermost/mattermost` 오픈소스 저장소를 직접 얕은 클론(최신 커밋 하나만 받는
방식)해서 서버 코드(`server/` 폴더)를 읽고 확인한 내용. 클론한 소스는 컴퓨터의 임시
작업 폴더(스크래치패드)에만 두었고, 우리 프로젝트 저장소에는 올리지 않았다 — CLAUDE.md
규칙대로 Mattermost 소스는 "읽기만 하고 절대 수정하지 않는다"는 원칙을 지키기 위함이다.

목적: 우리가 만들 "팀 지식 공유 레이어"를 Mattermost와 어떻게 연결할지 정하기 위해,
Mattermost가 실제로 외부에 무엇을 열어주는지, 그리고 "플러그인"이라는 내장 확장 방식이
왜 우리 라이선스 규칙에 안 맞는지를 소스 코드 레벨로 확인했다.

---

## 1. 플러그인 방식은 왜 우리한테 안 맞는가 — 실제로 뜯어보니

Mattermost는 "플러그인"이라는 기능 확장 방식을 갖고 있다. 겉으로만 보면 "플러그인은
별도 프로그램(별도 OS 프로세스)으로 실행된다"고 알려져 있어서, 어쩌면 우리 규칙("완전히
분리된 프로그램이어야 한다")에 맞을 수도 있어 보였다. 실제로 확인해보니 반은 맞고 반은 아니다.

- 맞는 부분: Mattermost 서버가 플러그인 파일을 실제로 **자식 프로세스로 실행**하긴 한다
  (`exec.Command`로 플러그인 실행 파일을 띄움).
- 안 맞는 부분: 이 자식 프로세스는
  1. Mattermost 서버가 자기 안에 갖고 있던 파일을 직접 실행시켜서 띄우는 것이라(서버가
     플러그인의 생명주기를 관리 — 켜고 끄고를 서버가 결정), **독립적으로 배포/운영되는
     프로그램이 아니라 서버에 종속된 부속품**에 가깝다.
  2. 통신 방식이 우리가 아는 일반적인 웹 API(HTTP 요청/응답)가 아니라, **Go 언어 전용의
     내부 RPC(원격 프로시저 호출) 프로토콜**을 쓴다. 이건 공개된 표준 규격이 아니라
     Mattermost 서버 코드와 강하게 얽힌 사설 통신 방식이다.
  3. 같은 컴퓨터(같은 서버)에서 돌아가는 걸 전제로 만들어져 있다.

비유하면, 플러그인은 "회사 밖에 있는 별도 회사"가 아니라 "같은 건물 안에서 회사 내부
전용 무전기로만 소통하는 파견 직원"에 더 가깝다. 겉보기엔 몸은 따로 있어도, 실질적으로는
그 회사(서버)와 한 몸처럼 움직인다는 뜻이다. 그래서 이 방식은 우리가 지켜야 하는 "완전히
독립된 별도 프로그램" 요건에 맞지 않는다는 게 소스 코드로 재확인됐다.

반대로 지금부터 설명할 **REST API(정해진 웹 주소로 요청을 보내고 답을 받는 방식)**와
**WebSocket(연결을 계속 열어두고 실시간으로 정보를 주고받는 방식)**은, 우리가 짠 프로그램이
완전히 다른 컴퓨터·다른 프로세스에서 돌아가면서도 "손님" 자격으로 정식 대문을 통해 정보를
주고받는 방식이라 우리 규칙에 정확히 들어맞는다.

---

## 2. REST API로 할 수 있는 일 — 이미 공식 도구까지 갖춰져 있다

Mattermost는 `/api/v4/...`로 시작하는 정해진 웹 주소들을 통해 서버 기능 대부분을 외부에
열어두고 있다. 우리 프로젝트에 바로 쓸 만한 것들:

- **메시지 읽기**: 특정 채널에 있는 메시지 목록을 가져오는 기능
- **메시지 쓰기**: 봇이 답장을 보내는 기능
- **채널 멤버 조회**: 이 채널에 누가 들어와 있는지 확인하는 기능
- **웹훅(webhook) 관리**: 아래 4번에서 설명할 자동 알림 기능 설정

더 좋은 점은, Mattermost가 이 모든 요청/응답의 정확한 형식을 담은 **공식 클라이언트
코드(약 8,500줄짜리 파일)를 이미 공개**해두고 있다는 것이다. 즉 우리가 "이 API에 어떤
값을 보내야 하고 어떤 값이 돌아오는지"를 하나하나 실험하며 알아낼 필요 없이, 이 공식
코드를 참고 삼아 그대로 맞춰 쓰면 된다는 뜻이다. 이건 완전히 외부에서, 플러그인이
아니라 일반적인 방식으로 접근하는 걸 전제로 만들어진 공식 도구다.

---

## 3. WebSocket — 실시간으로 대화를 "엿듣는" 방법, 그리고 그게 아무나 되는 이유

봇이 "누가 메시지를 보냈는지"를 실시간으로 알아채려면, 계속 서버에 "새 메시지 있어요?"라고
반복해서 물어보는(폴링) 대신, 연결을 한 번 열어두고 서버가 알아서 알려줄 때까지 기다리는
방식이 훨씬 효율적이다. 이게 WebSocket이다.

Mattermost는 새 메시지 등록, 메시지 수정/삭제, 이모지 반응, 채널/팀 멤버 변경 등 다양한
사건이 벌어질 때마다 이걸 신호(이벤트)로 만들어서, 그 사건과 관련 있는 사람들에게
실시간으로 뿌려준다. 중요한 발견은, **이 신호를 받을 수 있는 자격이 "플러그인이냐
아니냐"가 아니라 "그 채널/팀에 진짜로 속해 있는 사람(또는 봇)이냐"로 결정된다**는
것이다. 서버 코드를 보면, 신호를 보내기 직전에 "이 연결을 가진 사용자가 이 채널의
실제 멤버인지"를 확인하는 절차가 있고, 이 확인만 통과하면 일반 사용자든 봇 계정이든
플러그인이든 상관없이 같은 방식으로 신호를 받는다.

**의미**: 우리가 만들 팀 지식 레이어가 플러그인일 필요가 전혀 없다. 봇 계정을 하나
만들어서 관련 채널에 초대해두기만 하면, 완전히 외부에 있는 우리 프로그램이 이 WebSocket
연결을 열어서 "누가 어떤 채널에서 뭘 썼는지"를 실시간으로 다 받아볼 수 있다.

## 4. 채널 종류와 권한 체계 — 이미 잘 만들어진 "누구에게 뭘 보여줄지" 규칙

Mattermost 안에서 "대화가 오가는 공간"은 코드 레벨에서 이미 4가지 종류로 딱 정해져
있다:

| 종류 | 코드상 표시 | 실생활 비유 |
|---|---|---|
| 공개 채널(Open) | `O` | 팀 전체 회의실 — 아무나 검색해서 들어올 수 있음 |
| 비공개 채널(Private) | `P` | 초대받은 사람만 들어가는 소회의실 (예: 기획팀만) |
| 1:1 다이렉트 메시지(Direct) | `D` | 딱 두 사람만의 개인 대화방 |
| 그룹 다이렉트 메시지(Group DM) | `G` | 서너 명이 모인 작은 개인 대화방 (채널은 아니지만 성격은 여전히 "개인적") |

그리고 이 넷을 두 그룹("개인적인 대화방인가" vs "팀 전체 성격의 공간인가")으로 한 번에
판단해주는 기능도 이미 코드 안에 마련되어 있다. 즉 "이 채널 타입이 뭐야?"라고 Mattermost한테
물어보기만 하면, 우리가 따로 복잡한 판단 로직을 짤 필요 없이 답이 바로 온다.

**권한(permission)/역할(role) 체계**는 이것과는 다른 축이다 — "채널이 어떤 성격이냐"가
아니라 **"이 사람이 이 채널/팀에서 뭘 할 수 있는 지위냐"**를 나타낸다:

- `channel_user`(그 채널의 일반 멤버) < `channel_admin`(그 채널 관리자) <
  `team_admin`(팀 전체 관리자) < `system_admin`(Mattermost 서버 전체 관리자)
- 계층이 위로 갈수록 "할 수 있는 일(권한) 목록"이 더 많아지는 구조로, 역할마다 그
  목록이 이미 정의되어 있다.
- "이 채널에 지금 누가 들어와 있는지" 물어보는 채널 멤버 목록 조회 기능도 API로 제공된다.

정리하면: **채널 종류(D/G/O/P)는 "이 공간의 성격이 개인적이냐 공개적이냐"를 알려주고,
권한/멤버십 정보는 "실제로 이 정보를 볼 자격이 있는 사람이 누구누구인지"를 알려준다.**
이 둘을 조합하면 "이 대화는 누구한테 보여줘도 되는가"에 대한 기초 정보를 Mattermost한테서
거의 공짜로 얻을 수 있다.

**의미**: 우리가 "이 정보를 팀원 전체에게 공유해도 되는지, 개인적인 내용이라 숨겨야
하는지"를 판단하는 로직을 만들 때, 이미 있는 채널 종류 구분과 멤버십 정보를 그대로
가져다 쓰면 된다. 처음부터 우리만의 접근 권한 체계를 새로 설계할 필요가 없다 — 이미
Mattermost가 "누가 이 채널을 볼 수 있는가"를 정확히 관리하고 있고, 우리는 그 정보를
그대로 물어봐서 따르기만 하면 된다.

다만 이건 어디까지나 힌트일 뿐, 완벽한 정답은 아니다. 공개 채널에서도 개인적인 잡담이
나올 수 있고, DM에서도 팀 지식이 될 만한 질문이 나올 수 있다. 그래서 실제 판별 로직을
어떻게 짤지는 다음 섹션에서 별도로 다룬다.

## 5. 우리 프로그램이 Mattermost에 "로그인"하는 방법 — 봇 계정

외부 프로그램이 Mattermost의 REST API나 WebSocket에 접근하려면 당연히 인증(로그인)
절차가 필요하다. Mattermost는 이런 용도로 **봇 계정**이라는 특수한 사용자 계정 개념을
제공한다 — 사람이 아니라 프로그램이 로그인해서 쓰라고 만들어둔 계정이다.

실제 인증에 쓰는 건 별도의 "봇 전용 토큰 종류"가 아니라, 일반 사용자 계정에도 발급할
수 있는 **개인 액세스 토큰(personal access token)**이라는 문자열이다. 이 토큰을 발급받아
우리 프로그램에 넣어두면, 그 토큰으로 REST API 요청도 보내고 WebSocket 연결도 열 수
있다.

실제로 관리자가 해야 할 일은 이렇다: (1) 관리자 화면(시스템 콘솔)에서 봇 계정 만들기
기능을 켠다, (2) 봇 계정을 하나 만든다, (3) 그 봇 계정용 개인 액세스 토큰을 발급받는다,
(4) 그 봇을 필요한 팀/채널에 초대한다. 이건 **한 번만 하면 되는 설정**이고, 토큰에
별도 만료 기간을 정하지 않으면 계속 유효하기 때문에, 이후 반복해서 관리할 일이 거의
없다. 비개발자 팀이 부담 없이 할 수 있는 수준의 초기 설정이라고 볼 수 있다.

### 이 네 단계는 사람이 손으로 안 해도, 설치 스크립트가 대신 할 수 있다

위 네 단계(봇 계정 허용 켜기 / 봇 계정 만들기 / 토�큰 발급 / 채널 초대)는 전부 REST
API 호출로도 똑같이 처리할 수 있는 작업들이다. 즉 관리자가 매번 화면에서 클릭하는
대신, **설치 스크립트가 서버를 띄우는 김에 자동으로 다 처리**하도록 만들 수 있다.

- "봇 계정 만들기 기능을 켠다"는 설정값도 관리자 화면 토글이 아니라 **환경변수로
  미리 지정**해둘 수 있다는 걸 소스에서 확인했다 (Mattermost는 설정 항목마다
  `MM_설정영역_설정이름` 형태의 환경변수로 값을 미리 지정해두는 구조를 갖고 있다,
  `server/config/environment.go`).
  이러면 서버가 켜지는 순간부터 이미 그 설정이 켜진 상태로 시작한다.
- Mattermost는 설치 직후 **가장 먼저 가입한 사용자가 자동으로 관리자가 되는 구조**라,
  이 최초 가입도 스크립트가 가입 API를 호출해서 대신 처리할 수 있다.
- 그 뒤 봇 계정 생성, 토큰 발급, 채널 초대까지 전부 그 관리자 권한으로 스크립트가
  자동 수행할 수 있다.

**의미**: 이 제품을 유료로 배포한다고 할 때, 고객(팀)이 관리자 화면을 열어서 직접
설정을 만질 필요 없이, "설치 스크립트 한 번 실행"만으로 Mattermost와 우리 프로그램이
바로 대화할 수 있는 상태까지 자동으로 갖춰질 수 있다.

## 6. 서버 구성 — 물리적으로 나눌 필요 없이, 한 서버 안에서 Docker로

Mattermost, 우리 팀 지식 레이어, Hermes를 실제로 배포할 때, 이 세 프로그램을 각각
다른 물리 서버에 나눠 띄울 필요는 없다. **서버 한 대 안에서 Docker 컨테이너로 세
개를 각각 띄우는 방식이 라이선스 요건도 지키면서 운영 부담도 가장 적다.**

앞서(1번 항목) 설명한 "완전히 분리된 프로세스여야 한다"는 규칙은 **물리적으로 다른
컴퓨터에 있어야 한다는 뜻이 아니라, 프로그램끼리 한 몸으로 결합되지 않고 각자 독립된
프로세스로서 네트워크 통신(REST API, WebSocket)만으로 대화하면 된다**는 뜻이다.
Docker 컨테이너는 같은 서버 안에 있어도:

- 컨테이너마다 완전히 분리된 프로세스·파일시스템으로 실행되고,
- 컨테이너끼리는 오직 네트워크(Docker 내부 네트워크)를 통해서만 통신한다 — 이는 물리적으로
  다른 서버 두 대가 인터넷으로 통신하는 것과 구조적으로 동일하다.

즉 "Mattermost 컨테이너 + 우리 팀 지식 레이어 컨테이너 + Hermes 컨테이너"를 한 서버에서
Docker로 같이 띄워도, 서로 REST/WebSocket으로만 대화하는 한 여전히 "완전히 분리된
프로그램" 요건을 만족한다.

**실무적으로도 서버 한 대가 유리한 이유**:
- 관리할 서버가 하나뿐이라 비개발자 팀 입장에서 운영 부담이 적다.
- Hermes와 Mattermost 둘 다 공식 `docker-compose.yml`을 이미 제공하고 있어서, 이를
  참고해 우리 것까지 합친 통합 compose 파일 하나로 세 프로그램을 한 번에 켜고 끌 수
  있다.
- 서버를 여러 대로 나누면 비용이 늘고, 컨테이너 간 통신도 인터넷을 거치게 돼 오히려
  더 복잡해지고 느려진다.

---

## 7. 슬래시 커맨드 — `@멘션` 말고 `/명령어`로 부르는 방법도 가능

지금까지는 "봇을 `@봇이름`으로 멘션하면 반응한다"는 방식만 얘기했는데, Mattermost에는
`/명령어` 형태로 입력하면 반응하는 **슬래시 커맨드**라는 기능도 따로 있다. 예를 들어
`/요약 이번주 회의 정리해줘` 같은 식으로 쓸 수 있게 만들 수 있다.

확인해본 결과, 이 기능도 **플러그인이 필요 없다.** 동작 방식은 "누군가 그 명령어를
입력하면, Mattermost 서버가 미리 등록해둔 우리 프로그램의 웹 주소로 그 내용을 실어서
요청을 보내주는" 구조다 (앞서 설명한 아웃고잉 웹훅과 비슷한 원리). 관리자가 시스템
콘솔에서 "이 명령어(`/요약`)를 쓰면 이 주소로 보내라"고 한 번 등록해두기만 하면 끝이다.

**의미**: `@멘션` 방식보다 `/명령어` 방식이 비개발자에게 더 명확하고 배우기 쉬울 수
있다 (자동완성도 지원됨). 우리 프로젝트의 사용자 경험(UX)을 설계할 때 후보로 고려할
만하다.

---

## 8. 검색 API — 팀 지식을 다시 찾아보는 기능도 이미 있다

Mattermost는 키워드로 과거 메시지를 검색하는 기능을 REST API로 이미 제공한다. 검색
조건으로 채널, 작성자, 날짜 범위, 검색어(그리고 특정 단어 제외) 등을 지정할 수 있고,
결과로는 메시지 원문과 함께 "어느 부분이 검색어와 일치했는지" 표시 정보까지 같이
돌아온다.

**의미**: 우리가 만들 "팀 지식 조회" 기능에서, 처음부터 검색 엔진을 새로 만들 필요 없이
이 기존 검색 API를 활용해 "과거에 이런 얘기 나온 적 있나?"를 찾아보는 기반으로 쓸 수
있다.

## 9. 종합 — TeamBrain 설계에 주는 의미

- **플러그인은 확실히 피해야 한다.** 소스 코드로 봐도 플러그인은 Mattermost 서버에
  종속된 부속품에 가깝고, 우리가 지켜야 하는 "완전히 독립된 프로그램" 요건과 거리가
  있다.
- **REST API + WebSocket 조합만으로 필요한 걸 다 할 수 있어 보인다.** 메시지 읽기/쓰기,
  실시간 이벤트 수신, 채널 정보/멤버십 조회, 검색까지 전부 공식적으로 열려 있는 통로를
  통해 가능하다.
- **접근 제어(누구에게 뭘 보여줄지)를 새로 설계할 필요가 없다.** 채널 종류 구분과
  멤버십 조회 기능을 그대로 가져다 쓰면 된다.
- **초기 설정은 비개발자도 감당할 수 있는 수준으로 보인다.** 봇 계정 만들기 → 토큰
  발급 → 채널 초대, 이 세 단계면 우리 프로그램이 Mattermost와 대화할 준비가 끝난다.
- **이 초기 설정조차 고객이 손댈 필요 없이 설치 스크립트로 자동화할 수 있다.** 환경변수
  설정, 최초 관리자 가입, 봇 계정/토큰 발급, 채널 초대까지 전부 API로 되는 작업이라,
  유료 배포 시 "설치만 하면 바로 쓸 수 있는" 상태로 만들 수 있다.
- **물리적으로 서버를 나눌 필요가 없다.** Mattermost·팀 지식 레이어·Hermes를 서버 한
  대 안에서 각각 Docker 컨테이너로 띄우고 네트워크로만 통신해도, "완전히 분리된
  프로그램" 요건은 그대로 지켜진다. 운영 부담과 비용 면에서도 이 구성이 유리하다.
- **`/명령어` 방식이 `@멘션` 방식의 대안이 될 수 있다.** 사용자 경험 설계 시 두 방식을
  같이 고려해볼 만하다.
