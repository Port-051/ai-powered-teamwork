## 1. Hermes의 Mattermost 어댑터가 이미 완성돼 있다 — 근거 3겹

- **소스 코드 직접 확인**: 동연·홍재가 각자 독립적으로 `plugins/platforms/mattermost/adapter.py`
  (1,280~1,281줄)를 읽음. 둘 다 같은 결론 — REST v4 인증(`GET users/me`)·발신(`POST posts`)
  + WebSocket(소켓 안 `authentication_challenge`), 재연결 2초→60초 지수 백오프+지터,
  401/403 시 영구 포기. (`experiments/hermes-mattermost/2026-07-08/{dongyeon,hongjae}/hermes-source-analysis.md`)
- **공식 문서와 교차검증**: `port_051/mattermost-api-deep-dive.md`가 Mattermost 공식 API 문서를
  별도로 조사해 대조 — "공식 문서 기반 조사와 실제 구현체가 정확히 일치".
- **실제 로컬 실행 확인**: 2026-07-07 여운호·김동연이 각자 로컬에서 `MATTERMOST_URL`/`MATTERMOST_TOKEN`만
  설정해 멘션 감지·스레드·채널별 세션 분리가 실제로 동작하는 걸 확인 (`port_051/open-issues.md`).

→ 코드 읽기 + 공식 문서 대조 + 실제 실행, 세 겹이 맞아떨어져서 이 부분은 사실로 취급해도 된다.

## 2. 라이선스 해석 불일치 발견 및 해소

`experiments/` 안의 두 분석 문서가 서로 다른 결론을 냈다는 걸 재검토 중 발견함.

- **동연님 분석**: "Hermes 소스는 안 고치고, Hermes 안에 플러그인 형태로 끼워 넣지도 않으며,
  완전히 독립된 별도 프로그램으로 실행한다"는 규칙을 전제로, plugins 폴더 방식도 이벤트 훅
  방식도 "같은 프로세스 안에서 도니까" 전부 배제하고 **외부 API 서버(`api_server.py`)만
  안전하다**고 결론.
- **홍재님 분석**: 그런 제약을 언급하지 않고 memory-provider 확장점(Hermes 프로세스 안에서
  동작)을 최선으로 추천.

**원문(`CLAUDE.md`)으로 재확인한 결과**: 실제 규칙은 "Mattermost 플러그인이나 내장 모듈
형태는 안 된다... 그러면 우리 IP가 **AGPL**의 적용을 받는다"이다. 이 규칙이 막는 건
**Mattermost(AGPL)의 파생저작물이 되는 것**이지, Hermes(MIT)와 한 프로세스에서 도는 것
자체가 아니다. Hermes는 카피레프트가 없으므로 Hermes 프로세스 안에 있는 것은 이 규칙과
무관하다. `port_051/open-issues.md`의 2026-07-08 홍재님 각주("A안의 '훅'은 반드시 Hermes
자체 프로세스의 확장점을 의미해야 함, Mattermost 플러그인과 혼동 주의")가 이걸 정확히
짚고 있다.

→ **동연님의 "api_server만 안전하다"는 결론은 규칙을 원문보다 넓게 해석한 것으로 판단.**
게다가 api_server 방식은 실질적으로도 불리하다 — Hermes를 수동적 백엔드로만 쓰는 창구라
(a) Mattermost용 리스너를 결국 우리가 또 만들어야 해서 어댑터 재사용 이점이 사라지고
(b) 사람별 라우팅도 안 됨(3장 참고), (c) prefetch/sync_turn 같은 턴 단위 지식 주입·저장
훅도 못 쓴다.

## 3. 후보 방법 비교 (Mattermost/Hermes 통합 지점 — 판단 보류, 특징만 정리)

| | **어댑터 새로 짜기** | **코어 포크**(세션키 패치) | **api_server 단독** | **이벤트 훅**(`gateway/hooks.py`) | **memory-provider**(`agent/memory_provider.py`) |
|---|---|---|---|---|---|
| **무엇을 하는 방법인가** | Mattermost REST/WebSocket에 직접 붙는 우리 전용 프로그램을 처음부터 작성 | Hermes의 세션 키 생성 로직(`build_session_key()` 등)에 팀 ID를 끼워 넣도록 코어 자체를 수정 | Hermes를 그대로 켜두고, 우리 프로그램이 `api_server.py`가 여는 OpenAI 호환 API로 요청을 보내 대화를 이어감 | `~/.hermes/hooks/`에 핸들러 파일을 두면 세션/턴 시작·종료 등 이벤트를 옆에서 통지받음 | Hermes가 외부 메모리 공급자를 꽂는 공식 인터페이스에 우리 팀 지식 레이어를 provider로 등록 |
| **Hermes 코드/설정 변경** | 없음(Hermes와 무관하게 별도 존재) | 코어 코드 직접 수정(포크) | 없음(완전 순정) | 코드 수정 없음(핸들러 파일만 추가) | 코드 수정 없음(플러그인 등록 + `memory.provider` 설정값) |
| **확장점 성격** | 해당 없음 — 확장점을 안 쓰고 전부 우리가 구현 | 확장점 아님 — 코어 직접 수정 | 공식 기능(문서화된 API 창구) | 공식 기능(문서화됨), 다만 아직 아무 기본 내장 훅도 없는 상태 | 공식 기능(Honcho·Mem0 등 9종 외부 메모리가 실제로 쓰는 인터페이스) |
| **라이선스 관련** | 안전(별도 프로세스, Mattermost 소스 미변경) | 안전(Hermes=MIT, 포크·수정 법적으로 자유) | 안전(별도 프로세스에서 공개 API만 호출) | 안전(Hermes 자체 프로세스 안의 확장점, Mattermost와 무관) | 안전(Hermes 자체 프로세스 안의 확장점, Mattermost와 무관 — 2장 참고) |
| **실현 가능성(확인 상태)** | 가능 — 참고 구현체 있음(mmpy_bot 등, `mattermost-api-deep-dive.md` 05절), 다만 Hermes에 이미 동일 기능이 완성돼 있음이 확인됨 | 이론상 가능하나 호출부가 `gateway/run.py` 등 코드베이스 전역 십여 곳 이상에 흩어져 있음이 코드로 확인됨 | 창구 자체는 동작하나, 사람별 라우팅(주소로 구분)은 안 되는 것으로 코드 확인됨 | 동작 확인됨(코드로), 이벤트 컨텍스트가 메시지 500자로 잘려 전달됨 | 동작 원리 확인됨(코드로), `platform`/`user_id` kwargs 전달까지 확인 |
| **장점** | 요청 흐름 전체를 완전히 우리가 통제 | 세션 격리 개념 자체를 팀 단위로 원하는 대로 재정의 가능 | Hermes를 전혀 안 건드림 — 가장 "분리된 프로그램"에 가까운 형태 | 설치가 간단(핸들러 파일 하나), 알림·로깅류 부가 기능에 적합 | 업스트림 업데이트에 안 깨짐, 어댑터 재사용 이점 유지, 턴 단위 주입·저장이 정교하게 가능 |

| **유지보수 리스크** | 우리가 전량 부담(Mattermost API 변경 대응) | 높음(포크 유지보수, 병합 충돌) | 낮음(공식 API)이나 목적 달성엔 기능이 부족 | 낮음(공식 확장점)이나 용도가 우리 목적과 안 맞음 | 낮음(공식 인터페이스) |

이 표는 순수하게 각 후보의 특징을 같은 기준으로 나열한 것이고, 어느 쪽이 낫다는 결론은
여기서 내리지 않는다.

## 4. 팀 지식 공유·개인화 — 확인된 것 vs 미확인

### 팀 지식 공유 (기획서 주요기능2)
- **확인됨**: `prefetch(query, session_id=...)`(턴 시작 전 팀 지식 주입) /
  `sync_turn(user_content, assistant_content, session_id=..., messages=...)`(턴 종료 후 저장)
  훅에 `platform`/`user_id`/`agent_workspace`가 kwargs로 이미 들어옴 (`initialize(session_id, **kwargs)`).
- **미확인**: "이 세션이 어느 팀/워크스페이스 소속인지"를 어떻게 판별할지는 설계 안 됨
  (홍재님 본인이 "아직 안 풀린 것"이라고 명시).

### 개인화 (기획서 주요기능3)

**먼저 — Hermes에는 "분리"가 두 층이다** (동연, 2026-07-09 정리, `port_051/hermes-개인화-쉬운정리.md` 참고):
- **레벨 1(세션 격리)**: 한 채널에서 A·B가 각자 `@ai`를 부르면, 발신자 ID를 보고 **대화 기록**은
  기본값(`group_sessions_per_user=True`)으로 이미 사람별로 나뉜다. 단, 이건 "노트만 따로"인
  수준 — AI의 성격·자기모델·학습된 사용자 정보·스킬·설정은 안 나뉜다.
- **레벨 2(프로파일)**: `~/.hermes/profiles/<이름>/` 단위로 위 전부가 통째로 별개인, 완전히
  독립된 Hermes 한 벌. 기획서 "주요기능3 — 개인 학습 에이전트"가 실제로 요구하는 건 이쪽이다.
- 즉 **레벨 1은 봇 계정 하나로도 이미 자동으로 되고, 아래 A/B/C/D 논의는 전부 레벨 2를 어떻게
  얻을지에 대한 것**이다.

- **정정(2026-07-09)**: 이전 버전 이 문서와 07-08 공동분석은 "학습 요약이 MEMORY.md/USER.md에
  있고 발신자 구분 없이 섞인다"고 서술했는데, 동연님이 코드로 재확인한 결과 **이건 부정확했다.**
  실제로는 서로 다른 파일 3개가 있다:
  - `SOUL.md` — AI의 성격/정체성(사람이 편집, `hermes_cli/default_soul.py`·
    `agent/prompt_builder.py:load_soul_md()`)
  - `MEMORY.md` — AI가 업무 중 스스로 적는 메모, 성격이 아니라 환경/작업 노트(`tools/memory_tool.py`)
  - `USER.md` — AI가 학습한 사용자 정보(`tools/memory_tool.py`)

  07-08 분석이 "MEMORY.md=성격/자기모델"이라고 부른 건 SOUL.md의 존재를 놓치고 역할을 잘못
  짚은 것. 레벨 1에서 세 파일 다 프로파일 단위로만 존재하고 발신자별로는 안 나뉜다는 결론
  자체는 유지되지만(SOUL.md·스킬·설정이 안 나뉜다는 게 확인됨), 지금까지는 **`USER.md`가
  세션(발신자) 단위로 이미 나뉘는지, 아니면 SOUL.md처럼 프로파일 전체가 공유하는지는
  코드로 명시 확인된 바 없어 미확인 항목**이었다.

- **확인됨(2026-07-09, 여운호 — `/Users/yeounho/.hermes/hermes-agent` 소스 직접 확인)**:
  **`USER.md`도 세션(발신자) 단위로 안 나뉜다. SOUL.md와 마찬가지로 프로파일 단위로만 존재한다.**
  근거:
  1. `tools/memory_tool.py:55-57` `get_memory_dir()`가 "profile-scoped memories directory"라고
     주석에 명시. USER.md는 이 디렉터리 안 파일(`tools/memory_tool.py:189`).
  2. `agent/agent_init.py:1247-1251` — `MemoryStore(...)` 생성자·`load_from_disk()` 호출
     어디에도 `session_id`/`user_id` 인자가 없음.
  3. `hermes_constants.py`(`_HERMES_HOME_OVERRIDE` contextvar)·`gateway/run.py:1372-1403`
     (`_profile_runtime_scope`)·`gateway/run.py:8229-8268`(`_start_one_profile_adapters`) —
     프로파일 전환은 **메시지 하나하나가 아니라 어댑터/연결이 시작될 때** 결정됨. Mattermost처럼
     상시 연결을 쓰는 플랫폼은 프로파일마다 별도 봇 연결이 필요하고, 그 연결로 들어오는
     모든 발신자가 같은 프로파일(같은 USER.md)을 공유한다.
  - **결론**: 레벨 1(세션 격리)은 대화 기록만 나누지, USER.md(학습된 사용자 정보)는 전혀
    안 나눈다 — **레벨 1만으로는 "나를 학습하는 개인 AI"(주요기능3)가 0%도 성립하지 않는다.**
    레벨 2(프로파일 분리, 방법 A/B/D)가 반드시 있어야 한다.
- **확인됨(검토된 방법 4가지)**: (A) 팀원별 봇 계정+Hermes 프로파일, (B) 봇 계정 하나+발신자
  감지 커스텀 코드, (C) 외부 API 창구(api_server)에서 주소로 사람 구분, (D) Hermes를 팀원
  수만큼 통째로 복제. 이 중 **C는 코드로 확인한 결과 실현 불가능**해서 실제 후보는 A/B/D
  셋으로 좁혀짐(상세는 4-1 표 참고).
- **미확인**: A/B/D 중 무엇을 쓸지 미정, 셋 다 아직 실제로 구현해 동작시켜본 적 없음.

#### 4-1. 개인화 방법 A/B/C/D 상세 비교 (2026-07-09, 판단 보류 — 특징만 정리)

| | **방법 A** — 팀원별 봇 계정 + Hermes 프로파일 | **방법 B** — 봇 계정 하나 + 발신자 감지 코드 | **방법 C** — api_server 주소로 사람 구분 | **방법 D** — Hermes를 팀원 수만큼 복제 |
|---|---|---|---|---|
| **실현 가능한가** | 예 | 예 | **아니오 — 코드로 확인됨** (`webhook`엔 있는 주소 기반 사람 구분 기능이 `api_server`엔 없음, 한 프로세스가 시작 시 프로파일 하나에 고정) | 예 |
| **사용자가 부르는 봇** | 사람마다 다른 봇(`@ai-여운호`, `@ai-김동연` 등) | 봇 하나(`@ai`) 공용 | 봇 하나(`@ai`)를 의도했으나 실현 불가로 무의미 | 봇 하나(`@ai`) 공용 |
| **발신자 판별 위치** | 없음 — "어느 봇 연결로 왔는가"로만 자동 구분(Hermes 내장 로직) | Hermes 프로세스 안(우리 코드가 확장 지점에 얹음) | 시도: 요청 주소(예: `/p/여운호/...`)로 구분 — 실패 | 우리 레이어 안(Hermes 바깥) |
| **Hermes 코드/설정 변경** | 설정만(`multiplex_profiles: true`), 코드 변경 없음 | 코드 추가 필요 | 없음(완전 순정) — 그러나 목적 달성 자체가 안 됨 | 없음(완전 순정) |
| **확장점 성격** | 공식 기능(프로파일) | **비공식** — 코드 구조상 가능한 걸 확인한 수준, 공식 문서화 안 됨 | 공식 기능(api_server 자체는 공식)이나 사람별 라우팅 기능은 없음 | 공식 기능(`api_server`, 외부에서 호출) |
| **프로세스 수** | 1개(Hermes 하나가 여러 프로파일 동시 서비스) | 1개 | 해당 없음(실현 불가) | 팀원 수만큼(N개) |
| **자원 사용** | 프로세스 1개 + 연결 여럿(자원 효율적) | 프로세스 1개 | 해당 없음 | 프로세스 N개, 팀 규모에 비례해 증가 |
| **오사용 시 위험** | A가 실수로(또는 의도적으로) B봇을 부르면 A의 기록이 B 프로파일에 섞일 수 있음 — 봇마다 "이 사람만 부를 수 있다"는 허용목록(Hermes 기존 `*_ALLOWED_USERS` 기능)을 사람 수만큼 별도로 걸어야 막힘 | 판별 로직이 Hermes 안에 있어, 그 로직 자체의 정확성에 의존 | 해당 없음 | 판별 로직이 100% 우리 코드에 있어 우리가 직접 테스트·통제 가능 |
| **UX 영향** | 팀원마다 다른 봇 이름을 기억/구분해야 함 — 특히 여러 명이 같이 보는 채널에서 "@ai 하나로 통일" 픽스와 어긋남 | 기획서의 "@ai 멘션 하나" UX와 그대로 일치 | 해당 없음 | 기획서의 "@ai 멘션 하나" UX와 그대로 일치 |
| **유지보수 리스크** | 낮음(공식 기능만 사용) | Hermes 업스트림 업데이트 시 깨질 가능성 있음(비공식 확장점) | 해당 없음 | 낮음(공식 `api_server` 호출만 사용, Hermes 내부 구조 변화에 영향 덜 받음) |
| **설정/운영 복잡도** | 팀원 늘 때마다 봇 계정 발급 + 허용목록 설정 반복 | 낮음(봇 계정 하나) | 해당 없음 | 팀원 늘 때마다 Hermes 인스턴스 하나 더 띄우고 포트/라우팅 테이블 관리 |
| **팀 지식 공유(memory-provider)와의 관계** | 무관하게 병행 가능 — 각 프로파일 안에 동일한 memory-provider 플러그인을 꽂으면 됨 | 동일 | 해당 없음 | 동일 — 각 인스턴스마다 같은 memory-provider 플러그인을 꽂아 같은 팀 지식 저장소를 바라보게 하면 됨 |

네 방법 모두 "팀 지식 공유"(memory-provider) 설계와는 독립적으로 검토된 것 — 이 표는
순수하게 "개인화를 어떻게 분리할 것인가"에 대한 비교이고, C를 포함해 어느 쪽을 택할지는
이 문서에서 결론 내리지 않는다(C는 실현 불가로 이미 제외됨).

## 5. 결론 및 신뢰 수준

"이 구조(Mattermost ⇄ Hermes 재사용 ⇄ memory-provider 확장점 ⇄ 우리 원본 레이어)가 맞다"는
근거는 **코드를 두 사람이 따로 읽고, 공식 문서·실제 실행으로 교차검증한 수준까지는 확실**하다.

**2026-07-10 갱신 — 아래 "다음 단계" 1~3번 전부 실제로 만들어서 검증 완료.** 상세 결과는
`experiments/hermes-mattermost/2026-07-10/unho/mvp-multiprofile-validation.md` 참고. 요약:

- **(ㄴ) 레벨 2(학습된 사용자 정보까지 사람별로 다름)를 실제로 구현·검증**했다 — 전제 질문 1번은
  "레벨 2, 방법 A"로 실증 완료. `USER.md`/`MEMORY.md` 둘 다 프로파일별로 완전히 분리됨을 파일
  레벨로 확인.
- **방법 A(팀원별 봇 계정 + Hermes 프로파일)를 실제로 만들어 검증** — 세션 분리, 사람별 접근
  차단(`MATTERMOST_ALLOWED_USERS`), DM 시나리오, 동시성, SOUL.md 커스터마이징, launchd
  재시작 내구성까지 전부 실제 Mattermost 왕복으로 통과.
- **memory-provider 스켈레톤(`teambrain` 플러그인, 코드 사본 `experiments/hermes-mattermost/2026-07-10/unho/teambrain-plugin/`)을 만들어 (a) prefetch/sync_turn이 우리 코드까지 실제로 불려오는지,
  (b) 세션→팀 매핑이 실제로 가능한지 검증** — 둘 다 데이터 레벨로 확인됨(sync_turn이 공유
  저장소에 기록, prefetch가 다른 프로파일이 남긴 정보를 정확히 찾아 반환). 다만 라이브 Mattermost
  왕복에서는 OpenRouter 무료 모델의 크레딧 소진으로 모델이 주입된 컨텍스트를 실제로 활용하는
  것까지는 깔끔하게 확인 못 함 — **설계 결함이 아니라 그날의 무료 모델 쿼터 한계**로 판단, 크레딧
  여유 있는(또는 유료) 모델로 재확인 필요.

**남은 것**: 이번 검증은 여운호 1인이 로컬 도커 Mattermost에서 진행한 것이라, 실제 팀원
계정(김동연·신홍재)으로의 확장과 "세션→팀 매핑"의 프로덕션 설계(어느 팀/워크스페이스 소속인지
판별하는 방식)는 아직 미검증·미설계 상태다.
