## 전체 그림

```
Mattermost(순정) ── @ai 멘션 ──▶ Hermes 내장 Mattermost 어댑터(그대로 재사용)
                                        │
                                   memory-provider 확장점(공식 소켓)
                                        │
                            ★ 우리가 만드는 팀 지식 레이어 ★
                            (prefetch=팀지식 주입, sync_turn=팀지식 저장)
                                        │
                              LLM 리셀러 레이어(가상 키 방식)
                          Gemini/GLM 등 여러 무료·유료 공급자를 우리 계정 1개로 묶어서 중계
```

## 근거와 이유

1. **Mattermost 어댑터는 새로 안 짬** — 이미 완성돼 있고(1,281줄), 세션 격리·멘션 게이팅·페어링까지 검증됨. 재구현은 낭비.
2. **팀 지식 공유는 memory-provider로** — 코드 수정 없이 공식 소켓에 우리 레이어만 꽂으면 됨. Hermes(MIT)라 라이선스 문제도 없음.
3. **LLM 크레딧은 리셀러 패턴으로** — 팀원 각자 계정을 만들게 하지 말고, 우리가 API 키 1~소수 개를 계약하고 내부적으로 "가상 키"로 사람별 사용량만 장부 관리. 이게 표준 사업 구조고 확장성도 좋음.

## 지금 판단이 필요한 지점 — 개인화 범위를 어디까지 MVP에 넣을지

이게 유일하게 남은 진짜 설계 결정입니다. 두 갈래:

- **최소 범위(추천)**: MVP는 **세션 격리(사람별 대화 기억)까지만**. 이건 Hermes가 이미 공짜로 해주니 개발 비용 0. "각자 성격이 다르게 진화하는 개인 에이전트(USER.md 분리)"는 8월 이후 고도화로 미룸.
- **풀 범위**: 처음부터 방법 D(팀원 수만큼 Hermes 인스턴스 + 우리 레이어가 발신자별 라우팅)까지 구현. UX는 완벽(`@ai` 하나)하지만 인프라 복잡도·개발 시간이 MVP 일정(7/16)에 부담.

**추천 이유**: 기획서의 핵심 차별점("팀이 똑똑해진다")은 memory-provider 하나로 이미 MVP에서 체험 가능하고, "개인화 완성도"는 없어도 데모가 죽지 않습니다. 반면 인스턴스 N개 라우팅은 아직 검증도 안 됐고(프로토타입 전무) 일정 리스크가 큽니다. **최소 범위로 먼저 출시하고, 세션 격리만으로도 팀 지식 공유 체험이 되는지 도그푸딩으로 확인한 뒤, 필요성이 확인되면 개인화를 얹는 순서**가 안전하다고 봅니다.
