# TeamBrain

## 열린 질문

- **저희 목표 중 하나는 "팀원 각자에게 자신을 학습하는 개인 AI가 붙는 것"인데, 서버 한 대에
  Hermes를 하나만 띄워서 팀 전체를 처리하는 방식으로는 이 목표를 달성하기 어렵다는 것을
  확인했습니다. 이 부분을 어떤 방식으로 해결하면 좋을지 여쭤보고 싶습니다.**
  Hermes 소스 코드를 분석해보니, 대화 기록 자체는 팀원별로 잘 나뉘어 저장되지만, "이
  사람은 이런 성향이다" 같은 학습된 요약 정보(MEMORY.md/USER.md)는 팀원 구분 없이 Hermes
  프로그램 전체에 단 하나만 존재하는 구조였습니다. 그래서 서버 하나로 팀 전체를 처리하면
  팀원들의 학습 정보가 한 파일에 섞여버리게 됩니다. 근거가 된 코드 분석은
  [`experiments/hermes-slack/2026-07-08/dongyeon/hermes-source-analysis.md`](./experiments/hermes-slack/2026-07-08/dongyeon/hermes-source-analysis.md)
  7번 항목에 정리해두었습니다. PLAN.md Phase 8에서 팀/멘토님과 함께 결정하고자 합니다.

- **위 문제의 해결책으로 "Hermes를 팀원 한 명당 하나씩 완전히 독립된 프로그램(프로세스)으로
  띄우는 방식"을 검토했는데, 이게 팀 규모가 커져도 괜찮을지 여쭤보고 싶습니다.** 이 방식은
  라이선스 요건은 깔끔하지만, 팀원 수만큼 Hermes 프로그램이 항상 켜진 채로 대기하게 됩니다.
  팀원이 수백 명이 되면 대부분 안 쓰는 프로그램까지 계속 띄워두는 셈이라, AWS로 치면 사람
  수만큼 EC2를 항상 켜두기보다는 요청이 올 때만 깨워서 처리하는 서버리스 방식(Lambda 같은
  개념)으로 가야 하지 않을까 싶은데, 의견을 여쭙고 싶습니다.

- **"팀 공유 지식"을 만들 때, 그 재료가 되는 대화를 Hermes(개인 AI) 쪽에서 읽어와야 할지,
  아니면 Mattermost(팀 메신저) 쪽에서 읽어와야 할지 여쭤보고 싶습니다.** Hermes에는 "각자가
  개인 봇과 1:1로 나눈 대화"가 쌓이고, Mattermost에는 "팀원들이 채널에서 서로 나눈 대화"가
  쌓입니다. 저희 생각에는 팀의 결정·노하우·맥락은 주로 채널 대화에 있으니 팀 지식의 원천은
  Mattermost 쪽이 맞고, Hermes의 개인 대화까지 팀 지식으로 끌어오면 오히려 프라이버시 문제가
  생길 것 같은데, 이 방향이 맞는지 확인받고 싶습니다. (두 경우 모두 DB 파일을 직접 읽기보다는
  각자가 공식적으로 제공하는 API를 통해 읽는 것을 전제로 합니다.)

- **지난번에 오픈소스 공개 방향으로 말씀해주셨는데, 그 이후에 반대 방향("메신저까지 직접 만드는
  SaaS")도 한번 검토해봤습니다.** 사업 방향을 "메신저까지 직접 만드는 SaaS"로 갈지, "오픈소스로
  공개하고 저희는 호스팅(운영 대행)만 파는" 방향으로 갈지 궁금합니다. 두 방향의 장단점을 아래처럼
  정리해봤는데, 저희끼리는 아직 어느 쪽이 더 나을지 판단이 잘 서지 않아서 의견을 여쭙고 싶습니다.
  - **A안: 메신저까지 직접 만드는 SaaS**
    - 장점: 우리 제품 전체를 100% 우리 마음대로 통제·브랜딩할 수 있고, 남의 오픈소스 라이선스 제약(AGPL 등)에 신경 쓸 일이 없습니다.
    - 단점: 실시간 통신·다중기기 동기화·알림 같은 메신저 기반 기능을 안정적으로 구현하는 것 자체가 큰 작업이라, 소마 기간 안에 정작 차별화 포인트인 "팀 지식 레이어" 쪽에 쓸 시간이 줄어들 위험이 있습니다.
  - **B안: 오픈소스 공개 + 호스팅(Mattermost·Hermes·저희 레이어 연결) 대행**
    - 장점: 검증된 메신저(Mattermost)를 그대로 쓰니 개발 리소스를 팀 지식 레이어에 집중할 수 있고, 오픈소스 공개 자체가 개발자 커뮤니티 신뢰·인지도(2-3차 세그먼트, `PLAN.md` Phase 2-3 참고)로 이어질 수 있습니다. Mattermost 소스를 고치지 않고 API로만 연동하면 AGPL상 상업화(유료 호스팅)도 문제없다는 근거를 확인했습니다 (`PLAN.md` Phase 6 참고).
    - 단점: 메신저 자체의 UX·브랜딩을 저희가 완전히 통제할 수는 없고("Mattermost" 이름도 마케팅에 못 씀), Mattermost 쪽 정책 변화(라이선스, 기능 변경 등)에 어느 정도 영향을 받을 수 있습니다.

**Port_051 · SW Maestro 17기 (부산)**
팀원: 여운호 · 김동연 · 신홍재 / 멘토: 김선만

비개발자 팀이 평소 쓰던 업무 메신저에서 AI를 멘션(호출)하기만 하면, 팀의 일·결정·노하우가 저절로 쌓여 **"팀 공유 지능"**이 되고, 팀원 각자에게는 자신을 학습하는 **개인 AI**가 함께 붙는 협업 도구입니다.

터미널도, git clone도, 별도 노트 정리도 필요 없습니다. 메신저에서 AI에게 말 걸듯 일하면 끝입니다.

## 왜 필요한가

- 비개발자 팀은 AI를 개인이 산발적으로 쓰다 보니, 대화·결정·노하우가 각자 브라우저에 흩어져 팀 자산으로 남지 않습니다.
- 팀원이 휴가·퇴사하면 그가 알던 맥락이 통째로 사라집니다.
- 기존 지식 관리 도구(git 기반 등)는 비개발자에게 진입 장벽이 너무 높습니다.
- 상용 메신저 + AI 조합은 데이터가 외부 회사 서버를 거쳐, 업무 기밀 관점에서 부담이 됩니다.

## 어떻게 동작하는가

1. 팀이 자체 호스팅 오픈소스 메신저(Mattermost)를 자기 서버에 설치 → 모든 데이터가 우리 서버에만 남습니다.
2. 채널/DM에서 `@ai`를 멘션하면 AI가 응답합니다.
3. 모든 대화·결정·산출물이 자동으로 기억되어 팀 공유 뇌(팀 인텔리전스)와 개인 에이전트(Hermes 기반) 양쪽에 쌓입니다.

자세한 배경, 아키텍처, 라이선스 전략, 일정은 [`PLAN.md`](./PLAN.md)를 참고하세요.
