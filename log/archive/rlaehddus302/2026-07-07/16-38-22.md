### 왜 이런 일이 생기나

한 글자를 입력해도, API에 보내는 요청은 "그 한 글자"가 아니라 **"이전 대화 전체 + 그 한 글자"**입니다. 그래서:

- 1턴: 대화 100자 → 요청 100토큰
- 2턴: 대화 200자 (1턴 내용 + 새 내용) → 요청 200토큰
- 3턴: 대화 300자 → 요청 300토큰
- ...

대화가 길어질수록 **매 턴 보내는 토큰 수가 계속 늘어나고**, 그만큼 비용도 매 턴 늘어납니다. 사용자가 입력한 건 한 글자뿐이어도, 청구서에는 "이전 대화 전체를 다시 읽은 값"까지 다 찍힙니다.

### 이게 바로 지금까지 나온 장치들이 존재하는 이유

1. **컨텍스트 창 한계** — 어차피 무한정 늘어날 수 없으니 물리적으로 끊기는 지점이 있음 (앞서 설명)
2. **압축/요약(compaction)** — Claude Code 같은 도구엔 `/compact` 명령이 있어서, 대화가 길어지면 오래된 부분을 요약본으로 바꿔서 토큰 수를 확 줄임. Hermes의 **MEMORY.md**도 같은 발상 — 원문 대화 대신 압축된 핵심만 매번 붙임
3. **세션 리셋 정책** — Hermes가 "하루 지나면 리셋" 또는 "일정 시간 안 쓰면 리셋"(기본 1440분)하는 것도, 대화가 무한정 누적되는 걸 막는 장치
4. **필요할 때만 검색(session_search)** — 오래된 대화는 아예 매번 안 붙이고 저장만 해뒀다가, 진짜 필요할 때만 검색해서 그 부분만 끄집어냄
5. **프리픽스 캐시** — 이건 토큰 수 자체를 줄여주는 게 아니라, "어차피 반복되는 앞부분은 다시 계산 안 해도 되니 더 싸고 빠르게 처리해준다"는 것 — **비용을 완전히 없애진 못해도 늘어나는 속도를 완화**해주는 정도

### 정리

말씀하신 우려가 정확히 맞고, "대화가 길어질수록 비용이 계속 누적된다"는 건 이런 방식(전체 재전송)의 **근본적인 트레이드오프**입니다. 그래서 Hermes 같은 도구들은 "무조건 다 붙이기"가 아니라, 오래된 건 압축하거나(MEMORY.md), 아예 안 붙이고 검색용으로만 남겨두거나(session_search), 주기적으로 세션을 리셋하는 식으로 **누적 속도를 최대한 늦추는** 여러 장치를 겹겹이 써서 완화하는 겁니다. 완전히 없앨 수는 없는 문제입니다.
