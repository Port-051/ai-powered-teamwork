## 1. AI 기술 타당성 관련 총평

- 멘토님은 **AI 기술적 타당성/세부 구현**에 관심이 많았음. "앞단계(더 기본적인 문제)부터 해결됐는지"를 먼저 확인하려는 태도.
- "기술을 어떻게 축적할 것이냐"는 질문에 **데이터 중심**으로 봐야 한다고 강조.
- 지식 공유를 이야기하다가 "지식 증류(distillation)"에 빗댄 논의가 나왔고, 결국 우리가 쓸 용어는 **"지식 체계화"**로 정리됨.

## 2. 사업 전략 — 경쟁·타겟 (PLAN.md와 겹치는 부분 다수, 이번 멘토링에서 나온 논리 그대로 기록)

- **슬랙이 우리 아이디어를 베끼면?** / **Mattermost를 개량하는 거냐 대체하는 거냐?** / **이미 메신저 쓰는 시장에 셀링포인트가 있나 — 회사 메신저를 다 갈아야 하는 문제 아니냐** 라는 질문들이 나왔음. → 이 논리는 이미 PLAN.md Phase 2/5에 반영돼 있음 (데이터 노출 문제 → 자체 메신저, 자체 메신저 없는 중소기업 타겟, 슬랙이 못 따라오는 온프레미스·프라이버시 필터 방어선).
- **B2B 리스크**: 실사용자 확보가 어려움 → **최소 2~3개 기업 확보**가 필요하다는 점, 소마 인증에는 "시장을 보여주는 것"이 중요하다는 점 재확인.
- **달성 가능한 고객군을 우선 목표로 잡아라** / 기획서 방향(B2C/B2B/오픈소스 GitHub star)을 잘 정하라는 조언. **판매까지 안 해도 된다, 확보만 되면 된다** (홍재의 중소기업 네트워크 활용 언급).

### 2-1. 새로 나온 관점 — 네이버 사내 와이파이 사례

- 네이버가 사내 와이파이를 무료로 제공 → 직원들이 이를 이용. 감사실이 메신저 트래픽을 다 볼 수 있었고, 이 과정에서 사내 불륜이 적발되어 권고사직까지 간 사례가 있었다고 함.
- "회사가 동의서를 받았다 해도 내 개인정보를 들여다본다"는 반발감이 문제의 핵심.
- **AI 시대엔 달라질 수 있음**: 직원이 PC 2대(회사용/개인용)를 나눠 쓰는 식으로 회사 감시를 피하려 할 수 있고, 이러면 오히려 **회사 지식이 감시 밖의 개인 채널로 새어나가는(지식 누수) 보안 문제**가 생김.
- → 이 사례는 "왜 무작정 다 감시하는 방식이 아니라, AI가 알아서 회사용/개인용을 판별해 필터링하는 방식이 필요한가"를 뒷받침하는 근거로 쓸 수 있음.

### 2-2. 타겟 재검토 — "메신저 없는 회사가 지식 공유에 관심 있나?"

- 기존 논리(자체 메신저 없는 회사를 타겟)에 대한 반론: **"사내 메신저를 안 쓰는 이유가 있을 텐데"** (예: 돈이 없어서) → 그럼 무료로 제공하고 나중에 수익화하는 안?
- 더 근본적인 질문: **메신저 자체에 관심 없는 회사가 지식 공유(팀 브레인)에는 관심이 있을까?** → 메신저 유무만으로는 니즈를 보장 못 한다는 점, 지난 대화에서 이미 짚었던 문제의식과 일치.
- 멘토님이 새로 제시한 **1차 타겟 후보**: "**AI에 관심 있는 스타트업·중소기업**" — 이유는 ① 직원이 자주 바뀌어 퇴사·인수인계 이슈가 잦음, ② 인건비 절약 니즈.
  - ⚠️ 참고: 이건 우리가 이전에 정리한 "자체 메신저 없음 + 통증(지식유실/보안) 강함" 타겟 기준과는 결이 다른 축(메신저 유무가 아니라 "AI 도입 의지")이라, **PLAN.md 타겟 정의와 조율이 필요**함 — 아직 확정 아님.
- **틈새시장 조언**: 그냥 "니즈가 있는 곳"이 아니라 **"돈을 낼 의향이 있는 틈새시장"**을 찾으라는 조언.

## 3. 핵심 기술 챌린지 — 신규 논의 (이번 멘토링에서 가장 구체적으로 나온 부분)

멘토님과 정리한 **팀 브레인의 핵심 AI 모듈 2가지**:

### 3-1. 프라이버시 필터 (시크릿모드 판별)

- 목표: 대화 중 "회사에 공유해도 되는 내용" vs "개인 프라이버시로 남겨야 할 내용"을 AI가 판별해서 필터링/마스킹.
- 제안된 구조 — **2단계 판별기**:
  1. **1차 판별기 (룰 베이스)**: 키워드·가드레일 기반. 룰을 어떻게 정의할지는 미정 — **트리 구조** 등의 형태가 후보로 언급됨.
  2. **2차 판별기 (AI 컨텍스트 기반)**: 룰베이스로 못 거르는 애매한 경우를 AI가 문맥으로 판단.
- **AI 판별기 방식에 대한 비용 논쟁**:
  - 가장 단순한 방법은 "AI(LLM)가 스스로 판단"하게 하는 것이지만, 단점이 큼 — **비용(토큰, 가장 치명적)**, **정확도/신뢰도**, 레이턴시(단, 실시간성이 필수는 아니라 상대적으로 덜 중요).
  - 문제 제기: **"이진 분류일 뿐인데 굳이 비싼 디코더(LLM)를 써야 하나?"**
  - **대안**: 인코더 기반 모델(예: BERT류 — 약 8년 전 모델) 같은 가벼운 분류기로 이진 판별만 하는 방식.
- **검증 방법**: 실제 데이터와 지표가 필요함.
  - **가상 데이터셋 설계**: 개인챗 / 팀챗 / 그 중간의 **애매한 회색 지대 챗(가장 중요)** 세 종류로 구성.
  - 측정 지표를 별도로 정의해야 함 (아직 미정).

### 3-2. 지식 체계화 엔진

- 문제: 비정형 데이터(대화)를 구조화된 지식으로 뽑아내야 함.
- AI를 쓰더라도 컨텍스트 + 지침을 프롬프트로 줘야 하는데, **기업마다·업무마다 다 다르다**는 게 난제.
- "어떻게 구조화해야 지식 공유가 잘 될까?" — 이 과정 자체를 더 체계화해야 한다는 문제의식.
- 참고 사례로 언급된 것: LLM 메모리 압축 방식(엔진마다 자기 방식대로 압축), **팔란티어의 온톨로지** 접근.
- **대화가 왜 비정형인가**: 멀티턴 데이터라서 (싱글턴이 아님). 채팅은 1:1, 1:N, 시계열 등 여러 형태가 있는데, **다 한 번에 하려 하지 말고 하나부터 먼저 풀자**는 제안.

### 3-3. 전체 파이프라인 — 3개 핵심 모듈

```
필터(데이터 전처리) → 지식 엔진 → 답변 생성기
```

- "우리가 (기존 모델을 쓰는 게 아니라) **디코더를 직접 만들어야 할 수도 있다**"는 이야기까지 나옴 — 아직 방향 확정 아님, 검토 대상.
- **강력 추천**: 실제 데이터를 꼭 확보할 것 (예전 채팅 기록, 예전 아이디어 등). 가상 데이터만으로는 한계가 있음을 시사.
