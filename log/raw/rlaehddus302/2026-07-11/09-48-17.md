## 1. 코드 설명

`mattermost_search_mcp.py`를 위에서부터 보면:

**환경변수 읽기**
```python
MATTERMOST_URL = os.environ.get("MATTERMOST_URL", "").rstrip("/")
MATTERMOST_BOT_TOKEN = os.environ.get("MATTERMOST_BOT_TOKEN", "")
MATTERMOST_TEAM_ID = os.environ.get("MATTERMOST_TEAM_ID", "")
```
`config.yaml`의 `mcp_servers.mattermost_search.env`에 넣은 값들이 이 프로세스가 실행될 때 그대로 환경변수로 전달됩니다. 토큰을 코드에 하드코딩하지 않고 밖에서 주입하는 구조입니다.

**MCP 서버 객체 생성**
```python
mcp = FastMCP("mattermost-search")
```
`FastMCP`는 MCP Python SDK가 제공하는 헬퍼 클래스입니다. 이걸로 서버 이름을 정하고, 아래처럼 함수에 데코레이터만 붙이면 그 함수가 자동으로 "도구(tool)"로 등록됩니다 — MCP 프로토콜의 stdio 통신, JSON-RPC 메시지 처리, 스키마 생성 같은 걸 전부 대신 해줍니다.

**실제 검색 호출 (`_search`)**
```python
resp = requests.post(
    f"{MATTERMOST_URL}/api/v4/teams/{team_id}/posts/search",
    headers={"Authorization": f"Bearer {MATTERMOST_BOT_TOKEN}"},
    json={"terms": query, "is_or_search": is_or_search},
    timeout=10,
)
```
Mattermost 검색 REST API를 그대로 호출하는 부분입니다. `Bearer` 토큰으로 봇 계정 인증을 하고, `terms`에 검색어, `is_or_search`로 AND/OR를 정합니다.

**도구 함수 (`search_mattermost`)**
```python
@mcp.tool()
def search_mattermost(query: str, team_id: str = "", is_or_search: bool = False) -> list[dict]:
    """Mattermost 팀 대화(봇이 속한 채널 한정)에서 query로 메시지를 검색한다. ..."""
```
- `@mcp.tool()` 데코레이터가 이 함수를 MCP 도구로 노출시킵니다. **함수 시그니처(타입 힌트)와 docstring이 그대로 Hermes(LLM)에게 보여지는 도구 설명서**가 됩니다 — 그래서 docstring을 대충 안 쓰고 "봇이 속한 채널만 검색됨" 같은 제약까지 적어둔 겁니다. LLM이 이 설명을 보고 언제 이 도구를 호출할지, 어떤 인자를 넣을지 판단합니다.
- Mattermost 검색 API의 원래 응답 모양이 `{"order": [id1, id2, ...], "posts": {id1: {...}, id2: {...}}}` 처럼 **ID 배열 + ID→객체 딕셔너리**로 나뉘어 있어서 (검색 순서 정보와 실제 게시물 정보를 분리해서 준다), 그대로 LLM에게 넘기면 이해하기 번거롭습니다. 그래서 `order`를 순회하면서 `posts`에서 실제 내용을 찾아 평평한 리스트(`[{post_id, channel_id, user_id, message, create_at}, ...]`)로 다시 조립해주는 게 이 함수의 마지막 for문입니다.

**실행부**
```python
if __name__ == "__main__":
    mcp.run()
```
기본값으로 stdio transport를 씁니다 — Hermes가 이 파이썬 프로세스를 자식 프로세스로 띄우고 표준입출력(stdin/stdout)으로 JSON-RPC 메시지를 주고받는 방식입니다. `config.yaml`에서 `command`/`args`로 지정한 게 바로 이 프로세스를 실행하는 명령입니다.

## 2. Mattermost가 제공하는 검색 관련 API

지금 코드가 쓰는 것 외에, Mattermost REST API에 있는 검색/조회 계열을 정리하면:

| 엔드포인트 | 용도 | 비고 |
|---|---|---|
| `POST /api/v4/teams/{team_id}/posts/search` | **키워드 검색** (지금 코드가 쓰는 것) | `terms`에 검색어. Mattermost 자체 검색 문법 지원(아래 참고) |
| `POST /api/v4/teams/{team_id}/posts/search/autocomplete` | 검색창 자동완성용 힌트 반환 | 사람용 검색 UI를 흉내낼 때나 필요, 봇 용도로는 거의 안 씀 |
| `GET /api/v4/channels/{channel_id}/posts` | **채널의 최근 메시지 목록** (키워드 없이 그냥 시간순) | "최근 대화 훑기"용. 검색이 아니라 순수 조회라 별도 검색 문법 없음 |
| `GET /api/v4/posts/{post_id}/thread` | 특정 게시물의 스레드(답글) 전체 | 검색 결과 하나를 찾은 뒤 그 스레드 맥락까지 보고 싶을 때 |
| `GET /api/v4/teams/{team_id}/files/search` | **파일(첨부파일) 검색** | 파일명/내용 검색. Enterprise 라이선스 + Elasticsearch/OpenSearch 설정이 있어야 내용 검색까지 됨 (기본 OSS는 파일명 위주) |

**`posts/search`의 검색 문법(terms에 그대로 쓸 수 있음)**:
- `"정확한 문구"` — 따옴표로 구문 검색
- `from:사용자아이디` — 특정 사람이 쓴 메시지만
- `in:채널이름` — 특정 채널만
- `on:2026-07-01`, `after:2026-07-01`, `before:2026-07-01` — 날짜 필터
- `-단어` — 특정 단어 제외

이건 지금 코드의 `search_mattermost` docstring에서 "Mattermost 검색 문법 그대로 사용 가능"이라고만 써놓은 부분의 실제 내용입니다. 나중에 도구 설명을 더 구체화하고 싶으면 이 문법들을 docstring에 예시로 넣어주는 게 LLM이 더 정확한 쿼리를 만드는 데 도움이 됩니다.

**중요한 제약 (README에도 적어둔 것)**: `posts/search`는 **요청 주체(여기선 봇 토큰)가 멤버로 속한 채널만** 검색합니다. 시스템 관리자 권한을 줘도 이 필터는 그대로 적용됩니다 — "권한"과 "채널 멤버십"은 별개라서, 검색 범위를 넓히려면 봇을 해당 채널에 실제로 초대해야 합니다.

**OSS 검색의 한계**: 기본 설치(우리가 쓰는 순정 Mattermost)는 DB(PostgreSQL)의 텍스트 검색 기능을 그대로 씁니다. 데이터가 많아지거나 자연어 유사도 검색(의미 기반 검색)이 필요해지면 이걸로는 부족해서, 그때는 우리 팀 협업 지능 레이어 쪽에서 자체적으로 벡터 인덱스를 만들어 보강하는 걸 고려해야 할 수 있습니다 — 지금 프로토타입 범위 밖의 얘기지만 PLAN.md의 향후 과제로 적어둘 만합니다.
