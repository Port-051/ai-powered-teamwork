## 1. 개념 훑기 — Hermes 기억 시스템 제대로 파보기

### 파일 두 개가 전부다: MEMORY.md / USER.md

Hermes의 기억은 신비한 벡터 DB 같은 게 아니라, `~/.hermes/memories/` 안에 있는 **일반 markdown 파일 두 개**입니다.

- **`MEMORY.md`** (최대 약 2,200자 / 800토큰) — 에이전트 자신의 메모. 환경 정보("서버는 Debian 12 + PostgreSQL 16"), 프로젝트 컨벤션(들여쓰기 방식, 코딩 스타일), 발견한 도구의 특이사항, 완료한 작업, 배운 요령 등.
- **`USER.md`** (최대 약 1,375자 / 500토큰) — 사용자 프로필. 이름, 역할, 시간대, 소통 스타일 선호, 업무 습관, 기술 숙련도 등.

### 언제 읽고 언제 쓰는가

- **세션 시작 시**: 이 두 파일 내용이 통째로 시스템 프롬프트에 "얼려진 스냅샷"으로 주입됩니다. 각 항목은 `§` 기호로 구분되고, 헤더에 "MEMORY (your personal notes) [67% — 1,474/2,200 chars]" 식으로 사용률이 표시됩니다.
- **중요한 설계 포인트**: 이 스냅샷은 세션 시작 때 딱 한 번 캡처되고, **대화 도중에는 절대 바뀌지 않습니다.** 이유는 LLM의 프리픽스 캐시(같은 앞부분 텍스트를 재사용해서 비용·속도를 아끼는 기법) 성능을 지키기 위해서입니다. 즉 대화 중에 기억을 수정해도 디스크에는 바로 저장되지만, 그게 프롬프트에 실제로 반영되는 건 **다음 세션부터**입니다.
- 기억을 "읽는" 별도 명령은 없습니다 — 그냥 자동으로 시스템 프롬프트에 들어가 있는 것.

### 쓰는 방법: memory 도구의 3가지 동작

에이전트가 스스로 호출하는 `memory` 도구에는 딱 3가지 동작만 있습니다.

- **add** — 새 항목 추가
- **replace** — 기존 항목을 부분 문자열 매칭으로 찾아서 교체
- **remove** — 부분 문자열 매칭으로 찾아서 삭제

### 뭘 저장하고 뭘 버리는가 (이게 실제로 제일 흥미로운 부분)

**저장하는 것**: 사용자 선호("TypeScript 선호함"), 환경 사실, 사용자가 지적해준 교정사항이나 알아낸 우회법, 프로젝트 컨벤션, 완료한 작업(날짜 포함), 사용자의 명시적 요청.

**저장하지 않는 것**: 사소한 정보("사용자가 Python에 대해 물어봤음" 같은 것), 검색하면 금방 나오는 사실(언어 문법 문서화 내용), 대용량 데이터 덤프·코드블록·로그, 이번 세션에만 의미 있는 임시 경로, 이미 다른 컨텍스트 파일에 있는 내용.

→ 이 프로젝트(TeamBrain)를 만들 때 사실상 **"팀 공유 지능 레이어가 뭘 저장하고 뭘 버려야 하는지"에 대한 참고 기준**으로 그대로 가져다 쓸 수 있는 기준입니다.

### 용량이 꽉 차면?

**자동으로 오래된 걸 지우지 않습니다.** 용량 초과 상태에서 새로 쓰려고 하면 `memory` 도구가 에러를 반환하면서 현재 저장된 항목들을 같이 보여줍니다. 그러면 에이전트가 **같은 턴 안에서** 비슷한 항목들을 합치거나 지운 다음 다시 시도해야 합니다. 그래서 공식 권장은 "80% 이하로 유지"입니다.

### write_approval — 사용자가 검열할 수 있는 스위치

- 기본값(`false`): 에이전트가 자유롭게 씀. 대화 중간에 사용자가 시키지 않아도 백그라운드로 알아서 저장.
- `true`로 켜면: 저장이 전부 "대기" 상태가 되고, `/memory pending` (대기 목록 보기), `/memory approve <id>`, `/memory reject <id>` 명령으로 사람이 승인/거부해야 실제 반영됨.

### 세션 검색 — MEMORY.md와는 다른 기능

MEMORY.md/USER.md와 별개로, **모든 과거 대화 원문**은 `~/.hermes/state.db`라는 SQLite 파일에 저장됩니다. `session_search` 도구가 여기에 FTS5(SQLite 내장 전문 검색 엔진)로 키워드 검색을 해서, "몇 주 전에 나눴던 대화"를 기억 용량을 안 늘리면서도 찾아낼 수 있게 해줍니다. 즉:

- **MEMORY.md/USER.md** = 항상 프롬프트에 떠 있는 "요약된 핵심 메모" (용량 제한 있음)
- **session_search (FTS5)** = 필요할 때만 검색해서 불러오는 "원문 대화 아카이브" (용량 제한 사실상 없음)

이 두 계층 구조는 나중에 "팀 지능 레이어"를 설계할 때 그대로 참고할 만한 패턴입니다 — 항상 켜져있는 요약(팀 위키 같은 것) + 필요할 때 검색하는 원본 로그(채널 대화 전체).

### 외부 메모리 provider — 선택 사항, 한 번에 하나만

MEMORY.md/USER.md는 항상 켜져 있고, 여기에 **추가로** 외부 기억 서비스 하나를 붙일 수 있습니다(Honcho, Mem0, Hindsight 등 8종 중 택1). 이건 자동으로 대화 턴마다 관련 기억을 미리 가져오고(prefetch), 응답 후 동기화하고, 세션 종료 시 구조화된 기억을 추출합니다.

그중 **Honcho**만 조금 특이한데, "딸레틱(dialectic) 사용자 모델링"이라는 방식을 씁니다 — 그냥 키워드로 검색하는 게 아니라, "이 사람에 대한 요약(base layer)"과 "지금 대화 맥락에 맞춰 LLM이 실시간으로 추론한 보충 설명(dialectic layer)"을 따로 갱신 주기를 두고 관리합니다. 쉽게 말해 "이 사람이 누군지에 대한 고정 프로필" + "지금 이 순간 이 사람에게 필요한 추론"을 분리해서 다루는 방식.

- 우리 프로젝트는 지금 단계에서 외부 provider까지 쓸 필요는 없어 보이고, **내장 MEMORY.md/USER.md + session_search 구조만 이해해도 충분**합니다.

### (참고, 몰라도 되는 부분) 스킬·게이트웨이 등 나머지 기능

스킬 시스템은 "절차 기억" — 어려운 작업을 한 번 풀면 `~/.hermes/skills/`에 재사용 가능한 노하우 문서를 스스로 만들어 저장하고, `agentskills.io`라는 공개 표준을 따라 다른 사람 스킬도 가져다 쓸 수 있습니다. 이 외에 크론(예약 작업), 서브에이전트 병렬 실행, 음성 모드, 이미지 생성, MCP 연동, IDE 플러그인 등은 전부 "개인 비서 완성도"를 위한 부가 기능이라 TeamBrain 설계에는 직접 관련 없습니다.

## 2. Mattermost 게이트웨이 질문 — "굳이 어댑터를 만들어야 하나?"

찾아보니 중요한 사실이 있습니다: **Hermes는 이미 Mattermost용 게이트웨이를 내장하고 있습니다.** Slack, Discord뿐 아니라 Mattermost도 22개 지원 플랫폼 중 하나로, REST API v4 + WebSocket으로 붙는 어댑터가 이미 구현돼 있습니다(`MATTERMOST_URL`, `MATTERMOST_TOKEN` 환경변수만 설정하면 바로 동작).

**그럼 "①번 Mattermost 어댑터"를 우리가 밑바닥부터 새로 짤 필요는 없어졌다**고 봐도 됩니다 — 멘션 감지, 스레드 처리, 채널별 세션 분리 같은 기본 UX는 이미 다 구현돼 있음.

**다만 이게 PLAN.md의 핵심 novel 부분(②번 "팀 공유 지능 레이어")까지 해결해주진 않습니다.** Hermes의 Mattermost 어댑터는 "멘션한 사람 개인의 Hermes 인스턴스가 응답"하는 구조라서, 우리가 원하는 "여운호가 알아낸 걸 김동연 AI도 안다"는 팀 간 지식 공유는 기본 기능에 없습니다. 그래서 남는 선택지는 두 가지입니다:

- **A안**: Hermes의 Mattermost 어댑터를 그대로/포크해서 쓰고, 팀 지능 레이어는 그 파이프라인에 **플러그인이나 이벤트 훅**(`hermes plugins`, event hooks)으로 끼워 넣기 — 어댑터 재작성 노력을 아낄 수 있음.
- **B안**: 기존 계획대로 우리가 얇은 어댑터를 직접 짜서, Mattermost API와 Hermes 사이에서 팀 지능 레이어가 메시지를 가로채는 구조 — 제어권은 더 크지만 어댑터 구현 공수가 그대로 듦.

라이선스 관점(Phase 6, "우리 코드는 별도 프로세스여야 함")은 두 안 다 문제없어 보입니다 — Hermes 어댑터도 Mattermost 소스를 건드리는 게 아니라 API로만 붙는 별도 프로세스니까요.

이건 아키텍처 방향을 바꿀 만한 발견이라, PLAN.md Phase 8("팀 협업 인텔리전스 레이어 구체 설계 — 8월 재결정")에 이 옵션을 메모해두고 멘토님과 상의해보면 좋을 것 같습니다. 제가 임의로 어느 쪽으로 정하지는 않겠습니다.
