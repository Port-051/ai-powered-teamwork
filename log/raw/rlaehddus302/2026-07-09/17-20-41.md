## 방금 소스로 확인한 놀라운 사실

`tools/session_search_tool.py`의 `_discover()` 함수를 직접 열어보니:

- **사용자 필터가 아예 없습니다.** `subagent`/`tool` 소스만 빼고, **같은 DB 안의 모든 세션을 무차별로 검색 대상**으로 삼습니다.
- 심지어 `profile=` 인자를 주면 **다른 사람 프로파일의 DB까지 넘어가서 검색**할 수 있습니다 (`_resolve_profile_db()`).
- 그런데 이 교차검색에 **인가(authorization) 체크가 전혀 없습니다.** 프로파일 이름만 알면 그 사람 전체 대화 기록을 그냥 다 읽습니다 (`_resolve_profile_db:144-164` — 이름 존재 여부만 확인하고 바로 읽기 전용으로 엶).

즉 **"Hermes 내장 DB에서 찾기"는 기술적으로 이미 됩니다** — 별도 memory-provider를 안 만들어도, 팀 전체가 세션을 하나의 Hermes 인스턴스(또는 서로의 profile)에 담아두기만 하면 `session_search`가 알아서 사람 경계를 넘나들며 찾아줍니다.

## 다만 이게 "공짜"가 아니라 "위험을 다른 데로 옮긴 것"입니다

이 방법의 진짜 문제는 구현 난이도가 아니라 **권한 관리가 전혀 없다는 것**입니다:
- 사람 A의 DM에서 오간 민감한 얘기가 이 DB에 들어가 있으면, 사람 B가 물어봤을 때 **아무 필터 없이 그대로 튀어나올 수 있습니다.**
- 이건 지난번 언급한 팀의 기존 원칙("개인 DM은 팀 지식으로 승격 안 함, 공개 채널만")을 **Hermes 자체가 지켜주지 않는다**는 뜻이라, **"뭘 이 DB에 애초에 넣을지"를 우리가 미리 걸러야** 합니다.

## Mattermost 쪽은 "DB"가 아니라 "검색 API"로 해야 합니다 — 한 가지 정정

"Mattermost DB에서 찾기"라고 하셨는데, 정확히는 **Mattermost의 REST 검색 API**(`GET /api/v4/posts/search`)를 써야 합니다. CLAUDE.md 원칙(REST/WebSocket API만 사용, 소스·DB 직접 건드리지 않음)과도 맞고, **덤으로 권한 문제가 공짜로 해결**됩니다 — `decisions.md`가 이미 짚었듯, **질문한 사람 본인의 Mattermost 토큰으로 검색하면 그 사람이 못 보는 비공개 채널은 검색 결과에서 자동으로 빠집니다.** Hermes 내장 DB 방식과 정반대로, **이쪽은 권한 필터가 이미 내장**돼 있는 셈입니다.

## 정리 — 세 가지 방법 비교

| | Mattermost 검색 API | Hermes 내장 DB(session_search) | memory-provider(원래 제안) |
|---|---|---|---|
| 구현 난이도 | **가장 쉬움** (API 호출 + 프롬프트 삽입) | 쉬움(이미 됨) | 중간(직접 설계 필요) |
| 권한 필터 | ✅ 공짜(토큰 스코프) | ❌ 전혀 없음 | 직접 만들어야 함 |
| 데이터 형태 | Mattermost 원문 그대로 | Hermes가 나눈 세션 원문 | 우리가 원하는 형태로 가공 가능 |
