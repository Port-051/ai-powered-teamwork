# Mattermost↔Hermes 통합 방식 — memory-provider(A안) 근거 정리

> 2026-07-09, 여운호 정리. `PLAN.md` Phase 8 "Mattermost 통합 방식 A/B안"의 근거 문서.
> 배경: 시스템 구성도를 다시 그리다가 "Mattermost → 우리 어댑터 → Hermes"(기존 기획서 문장)가
> 근거 없이 그려진 그림이라는 걸 발견했고, 어느 구조가 맞는지 재검토를 요청받아 정리함.
> **이 문서의 성격**: 코드를 읽고 추론한 수준의 근거 정리이지, 실제로 프로토타입을 만들어
> 검증한 결과가 아니다. 아래 "확인된 것"과 "미확인"을 구분해서 읽을 것.

## 1. Hermes의 Mattermost 어댑터가 이미 완성돼 있다 — 근거 3겹

- **소스 코드 직접 확인**: 동연·홍재가 각자 독립적으로 `plugins/platforms/mattermost/adapter.py`
  (1,280~1,281줄)를 읽음. 둘 다 같은 결론 — REST v4 인증(`GET users/me`)·발신(`POST posts`)
  + WebSocket(소켓 안 `authentication_challenge`), 재연결 2초→60초 지수 백오프+지터,
  401/403 시 영구 포기. (`experiments/hermes-mattermost/2026-07-08/{dongyeon,hongjae}/hermes-source-analysis.md`)
- **공식 문서와 교차검증**: `port_051/mattermost-api-deep-dive.md`가 Mattermost 공식 API 문서를
  별도로 조사해 대조 — "공식 문서 기반 조사와 실제 구현체가 정확히 일치".
- **실제 로컬 실행 확인**: 2026-07-07 여운호·김동연이 각자 로컬에서 `MATTERMOST_URL`/`MATTERMOST_TOKEN`만
  설정해 멘션 감지·스레드·채널별 세션 분리가 실제로 동작하는 걸 확인 (`port_051/open-issues.md`).

→ 코드 읽기 + 공식 문서 대조 + 실제 실행, 세 겹이 맞아떨어져서 이 부분은 사실로 취급해도 된다.

## 2. 라이선스 해석 불일치 발견 및 해소

`experiments/` 안의 두 분석 문서가 서로 다른 결론을 냈다는 걸 재검토 중 발견함.

- **동연님 분석**: "Hermes 소스는 안 고치고, Hermes 안에 플러그인 형태로 끼워 넣지도 않으며,
  완전히 독립된 별도 프로그램으로 실행한다"는 규칙을 전제로, plugins 폴더 방식도 이벤트 훅
  방식도 "같은 프로세스 안에서 도니까" 전부 배제하고 **외부 API 서버(`api_server.py`)만
  안전하다**고 결론.
- **홍재님 분석**: 그런 제약을 언급하지 않고 memory-provider 확장점(Hermes 프로세스 안에서
  동작)을 최선으로 추천.

**원문(`CLAUDE.md`)으로 재확인한 결과**: 실제 규칙은 "Mattermost 플러그인이나 내장 모듈
형태는 안 된다... 그러면 우리 IP가 **AGPL**의 적용을 받는다"이다. 이 규칙이 막는 건
**Mattermost(AGPL)의 파생저작물이 되는 것**이지, Hermes(MIT)와 한 프로세스에서 도는 것
자체가 아니다. Hermes는 카피레프트가 없으므로 Hermes 프로세스 안에 있는 것은 이 규칙과
무관하다. `port_051/open-issues.md`의 2026-07-08 홍재님 각주("A안의 '훅'은 반드시 Hermes
자체 프로세스의 확장점을 의미해야 함, Mattermost 플러그인과 혼동 주의")가 이걸 정확히
짚고 있다.

→ **동연님의 "api_server만 안전하다"는 결론은 규칙을 원문보다 넓게 해석한 것으로 판단.**
게다가 api_server 방식은 실질적으로도 불리하다 — Hermes를 수동적 백엔드로만 쓰는 창구라
(a) Mattermost용 리스너를 결국 우리가 또 만들어야 해서 어댑터 재사용 이점이 사라지고
(b) 사람별 라우팅도 안 됨(3장 참고), (c) prefetch/sync_turn 같은 턴 단위 지식 주입·저장
훅도 못 쓴다.

## 3. 후보 방법 비교

| 방법 | 문제점 |
|---|---|
| 어댑터 처음부터 새로 짜기 (원래 B안) | 이미 풀린 문제(인증·재연결·멘션판별)를 다시 품, 재사용 이점 없음 |
| 세션 키 자체를 패치 (코어 포크) | 호출부가 코드베이스 십여 곳에 흩어져 있어 홍재님 본인이 비추천 |
| 외부 API 서버(api_server) 단독 | 사람별 라우팅 불가(코드로 확인됨) + 결국 어댑터 재구현 필요 |
| 이벤트 훅(`gateway/hooks.py`) | 메시지 500자로 잘려 옆에서 관찰만 가능, 지식 주입엔 약함 |
| **memory-provider (`agent/memory_provider.py`)** | 공식 문서화된 인터페이스, prefetch/sync_turn이 필요와 정확히 일치, 라이선스 안전 |

나온 후보들 중에서는 memory-provider가 압도적으로 우위. "이보다 나은 방법이 세상에
없다"까지 단언하는 건 아니다.

## 4. 팀 지식 공유·개인화 — 확인된 것 vs 미확인

### 팀 지식 공유 (기획서 주요기능2)
- **확인됨**: `prefetch(query, session_id=...)`(턴 시작 전 팀 지식 주입) /
  `sync_turn(user_content, assistant_content, session_id=..., messages=...)`(턴 종료 후 저장)
  훅에 `platform`/`user_id`/`agent_workspace`가 kwargs로 이미 들어옴 (`initialize(session_id, **kwargs)`).
- **미확인**: "이 세션이 어느 팀/워크스페이스 소속인지"를 어떻게 판별할지는 설계 안 됨
  (홍재님 본인이 "아직 안 풀린 것"이라고 명시).

### 개인화 (기획서 주요기능3)
- **확인됨**: 봇 계정 하나로 전체 팀을 처리하면 Hermes의 학습 요약(MEMORY.md/USER.md)이
  발신자 정보를 아예 안 받아서 팀원 전체가 하나로 섞임 (`port_051/decisions.md` PLAN.md
  Phase 8 항목 참고).
- **확인됨(해결 경로)**: 이를 푸는 3가지 방법 — (A) 팀원별 봇 계정+Hermes 프로파일,
  (B) 봇 계정 하나+발신자 감지 커스텀 코드, (D) Hermes를 팀원 수만큼 통째로 복제.
- **미확인**: 셋 중 무엇을 쓸지 미정, 셋 다 아직 실제로 구현해 동작시켜본 적 없음.

#### 4-1. 개인화 방법 A/B/D 상세 비교 (2026-07-09, 판단 보류 — 특징만 정리)

| | **방법 A** — 팀원별 봇 계정 + Hermes 프로파일 | **방법 B** — 봇 계정 하나 + 발신자 감지 코드 | **방법 D** — Hermes를 팀원 수만큼 복제 |
|---|---|---|---|
| **사용자가 부르는 봇** | 사람마다 다른 봇(`@ai-여운호`, `@ai-김동연` 등) | 봇 하나(`@ai`) 공용 | 봇 하나(`@ai`) 공용 |
| **발신자 판별 위치** | 없음 — "어느 봇 연결로 왔는가"로만 자동 구분(Hermes 내장 로직) | Hermes 프로세스 안(우리 코드가 확장 지점에 얹음) | 우리 레이어 안(Hermes 바깥) |
| **Hermes 코드/설정 변경** | 설정만(`multiplex_profiles: true`), 코드 변경 없음 | 코드 추가 필요 | 없음(완전 순정) |
| **확장점 성격** | 공식 기능(프로파일) | **비공식** — 코드 구조상 가능한 걸 확인한 수준, 공식 문서화 안 됨 | 공식 기능(`api_server`, 외부에서 호출) |
| **프로세스 수** | 1개(Hermes 하나가 여러 프로파일 동시 서비스) | 1개 | 팀원 수만큼(N개) |
| **자원 사용** | 프로세스 1개 + 연결 여럿(자원 효율적) | 프로세스 1개 | 프로세스 N개, 팀 규모에 비례해 증가 |
| **오사용 시 위험** | A가 실수로(또는 의도적으로) B봇을 부르면 A의 기록이 B 프로파일에 섞일 수 있음 — 봇마다 "이 사람만 부를 수 있다"는 허용목록(Hermes 기존 `*_ALLOWED_USERS` 기능)을 사람 수만큼 별도로 걸어야 막힘 | 판별 로직이 Hermes 안에 있어, 그 로직 자체의 정확성에 의존 | 판별 로직이 100% 우리 코드에 있어 우리가 직접 테스트·통제 가능 |
| **UX 영향** | 팀원마다 다른 봇 이름을 기억/구분해야 함 — 특히 여러 명이 같이 보는 채널에서 "@ai 하나로 통일" 픽스와 어긋남 | 기획서의 "@ai 멘션 하나" UX와 그대로 일치 | 기획서의 "@ai 멘션 하나" UX와 그대로 일치 |
| **유지보수 리스크** | 낮음(공식 기능만 사용) | Hermes 업스트림 업데이트 시 깨질 가능성 있음(비공식 확장점) | 낮음(공식 `api_server` 호출만 사용, Hermes 내부 구조 변화에 영향 덜 받음) |
| **설정/운영 복잡도** | 팀원 늘 때마다 봇 계정 발급 + 허용목록 설정 반복 | 낮음(봇 계정 하나) | 팀원 늘 때마다 Hermes 인스턴스 하나 더 띄우고 포트/라우팅 테이블 관리 |
| **팀 지식 공유(memory-provider)와의 관계** | 무관하게 병행 가능 — 각 프로파일 안에 동일한 memory-provider 플러그인을 꽂으면 됨 | 동일 | 동일 — 각 인스턴스마다 같은 memory-provider 플러그인을 꽂아 같은 팀 지식 저장소를 바라보게 하면 됨 |

세 방법 모두 "팀 지식 공유"(memory-provider) 설계와는 독립적으로 조합 가능 — 이 표는 순수하게 "개인화를 어떻게 분리할 것인가"에 대한 비교이고, 어느 쪽을 택할지는 이 문서에서 결론 내리지 않는다.

## 5. 결론 및 신뢰 수준

"이 구조(Mattermost ⇄ Hermes 재사용 ⇄ memory-provider 확장점 ⇄ 우리 원본 레이어)가 맞다"는
근거는 **코드를 두 사람이 따로 읽고, 공식 문서·실제 실행으로 교차검증한 수준까지는 확실**하다.
하지만 "팀 지식 공유·개인화가 이 구조 위에서 실제로 매끄럽게 동작한다"는 건 아직
**코드를 읽고 추론한 단계**이지 **실제로 만들어서 검증한 단계가 아니다.**

**다음 단계**: 8월 재결정을 진짜 "확정"으로 만들려면, memory-provider 스켈레톤을 하나 짜서
(1) prefetch/sync_turn이 실제로 우리 코드까지 잘 불려오는지, (2) 세션→팀 매핑이 실제로
가능한지를 작게라도 프로토타입으로 찍어보는 게 필요하다.
