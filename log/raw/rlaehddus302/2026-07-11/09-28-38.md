결론부터: **provider 자리는 아닙니다.** 방금 확인해보니 Hermes의 `providers/`는 "외부 저장소"가 아니라 **LLM 추론 제공자**(OpenAI, Anthropic 등 모델 API) 설정을 다루는 곳이었습니다 (`providers/base.py`: "A ProviderProfile declares everything about an *inference provider*"). 검색 기능을 붙일 자리가 아닙니다.

**진짜 정답은 MCP(Model Context Protocol)**입니다. Hermes에 이미 공식 확장 지점이 있습니다.

`tools/mcp_tool.py` 확인 결과, Hermes는 `~/.hermes/config.yaml`의 `mcp_servers` 항목에 외부 MCP 서버를 등록해두면, 그 서버가 제공하는 도구들을 **Hermes 소스 코드를 한 줄도 안 건드리고** 자동으로 에이전트 도구 목록에 끼워 넣어줍니다(stdio/HTTP로 통신하는 별도 프로세스). 이게 바로 기획서에서 말한 "공식 확장 지점을 통해 우리 원본 레이어가 꽂힌다"는 그 지점입니다.

**왜 이게 맞는 답인지:**

1. **CLAUDE.md의 "별도 프로세스" 요건과 정확히 맞음** — MCP 서버는 그 자체로 독립 프로세스라서, Mattermost 어댑터/플러그인처럼 짤 필요가 없습니다.
2. **Hermes 포크를 안 건드림** — `discord_tool.py`처럼 Hermes 소스 안에 새 파일을 추가하는 방식(전에 확인한 것처럼 Mattermost엔 없는 도구)도 가능은 하지만, 그러면 우리 코드가 Hermes 포크 안에 섞여 들어가서 나중에 업스트림 업데이트를 받을 때마다 병합 충돌 부담이 생깁니다. MCP 서버는 완전히 별개 저장소/프로세스라 이 부담이 없습니다.
3. **"연결부터 다시 만들어야 한다"는 걱정은 사실이 아닙니다** — 검색 기능은 `adapter.py`가 이미 하고 있는 "멘션 받고 그 자리에서 답장하는" 실시간 연결과는 완전히 별개의, **새로운 읽기 전용 연결**입니다. 봇 토큰으로 `POST /api/v4/posts/search` 같은 Mattermost REST API를 호출하는 코드 몇 줄이면 되고, 기존 어댑터의 WebSocket/실시간 응답 로직은 전혀 손댈 필요가 없습니다.

**정리하면 구조는:**

```
우리가 만드는 MCP 서버 (별도 프로세스)
  → Mattermost REST API 호출 (검색/조회, 봇 토큰 사용)
  → 결과를 도구 응답으로 반환
        ↑
Hermes (~/.hermes/config.yaml의 mcp_servers에 등록)
  → 대화 중 필요하면 이 도구를 스스로 호출해서 검색 결과를 답변에 활용
```
