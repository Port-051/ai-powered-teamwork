## 1. "Mattermost↔Hermes를 바로 이으면 개인화가 불가능하다" → 사실이 아닙니다

이게 핵심 오해예요. Hermes 소스(`gateway/session.py`)를 직접 확인했는데, Hermes는 **이미 채널 안에서 사람별로 세션(=기억)을 자동으로 갈라줍니다.**

- `build_session_key()`가 세션 키를 만들 때, 그룹/채널 메시지는 **보낸 사람의 user_id를 키에 넣어서 사람마다 다른 세션**으로 격리합니다 (`group_sessions_per_user=True`가 기본값, `session.py:818`).
- 즉 같은 채널에서 A가 `@ai`, B가 `@ai`를 불러도, **Hermes가 Mattermost user ID를 보고 알아서 A의 기억 / B의 기억을 분리**합니다.

> **다시 말해, 질문 2번에서 하려던 "봇 하나 + 발신자 감지로 프로파일 갈라주기"는 Hermes가 이미 네이티브로 하고 있는 일입니다.** 개인화 때문에 어댑터를 직접 짤 필요가 없어요.

그래서 구조가 충돌하지 않습니다:
- **팀 공유 지능** → memory-provider 확장점에 우리 로직
- **개인화** → Hermes가 user_id 기준으로 세션 자동 분리 (공짜)

두 개가 동시에 성립합니다.

**단, 주의할 점 2가지** (제 기억에 저장된 소스 분석 기준):
- **스레드는 기본이 "공유"**입니다 (`thread_sessions_per_user=False`). 스레드 안에서도 사람별로 갈라주고 싶으면 이 값을 `true`로 바꾸면 됩니다 — 설정 한 줄이지 코드가 아닙니다.
- **Mattermost 어댑터엔 히스토리 백필이 없습니다.** "봇 멘션 전의 대화 맥락까지 자동으로 따라온다"는 Mattermost에선 기본 제공 안 됩니다 (Discord/Telegram만 있음). 이건 우리 레이어에서 채워야 할 부분.

## 2. "봇 하나 + 발신자 감지" 방식 — 가능하고, 소스 안 건드리고도 됩니다

`api_server.py`를 보니 **`X-Hermes-Session-Key`라는 HTTP 헤더**를 지원합니다 (`api_server.py:1509`). 클라이언트가 요청마다 "이건 누구의 세션이다"를 직접 지정할 수 있어요.

즉 우리 어댑터(별도 프로세스)가:
1. Mattermost에서 메시지 받음 → 보낸 사람 user_id 확인
2. Hermes API 호출할 때 그 사람 전용 session key를 헤더로 넘김

이렇게 하면 **Hermes 소스를 한 줄도 안 건드리고**, 우리 코드 바깥에서 프로파일을 갈라줄 수 있습니다. 라이선스 문제 전혀 없습니다 (공개 API만 호출 = CLAUDE.md 제약 그대로 만족).

## 3. "지금 버전 받아서 우리 입맛대로 코드 고쳐 써도 되나?"

두 층위로 나눠야 해요.

**(a) 법적으로 되나?** → **네, 100% 됩니다.**
Hermes는 MIT 라이선스예요. MIT는 포크(복사본 떠서 따로 관리)·수정·특정 버전 고정·비공개 배포·상업적 이용 전부 허용합니다. **유일한 의무는 원본 MIT 저작권 고지를 유지하는 것** 하나뿐입니다 (CLAUDE.md 제약 #4). 그것만 지키면 마음대로 고쳐도 됩니다.

**(b) 우리 프로젝트 규칙상 해도 되나?** → **가급적 하지 말자고 우리가 이미 정해둔 부분입니다.**
CLAUDE.md 아키텍처 제약 #2는 "Hermes 소스를 안 건드리고 별도 프로세스에서 API만 호출한다"인데, 이건 **법적 강제가 아니라 우리 팀이 스스로 택한 설계 원칙**이에요. 이유는 두 가지:
- **업그레이드 가능성**: 소스를 안 고치면 나중에 Hermes 버그픽스·보안패치·신기능을 그냥 당겨올 수 있음. 소스를 고쳐서 포크하면 **그 순간부터 우리가 그 포크의 영구 관리자**가 됩니다 — 이후 모든 업스트림 변경을 손으로 병합해야 하고, 보안 업데이트도 끊깁니다.
- **깔끔한 라이선스 분리**: 별도 프로세스 = 우리 코드는 독립적으로 라이선싱 가능.

**그래서 판단 기준:**

| | 소스 안 건드리고 API/설정으로 (권장) | 소스 포크해서 수정 |
|---|---|---|
| 개인 프로파일 분리 | ✅ user_id 세션키로 됨 | 필요 없음 |
| 업스트림 업데이트 | ✅ 쉬움 | ❌ 매번 수동 병합 |
| 유지보수 부담 | 낮음 | 영구적으로 우리 몫 |
| 법적 문제 | 없음 | 없음(MIT, 고지만 유지) |
