## Hermes 멀티프로파일 방식 재검증 — 멀티플렉싱(B)이 Mattermost 인증에서 실패, 방법 A로 회귀 확정 — 팀 공유
- 09:23 "Hermes profile 기능으로 한 인스턴스를 여러 사람이 쓸 수 있다는데"에서 시작해, 어제(07-09) 결론(방법 A: 프로세스 각자 vs 방법 B: 멀티플렉싱)을 재검토. 처음엔 "사람이 늘면 자원을 너무 먹는다"는 이유로 B(멀티플렉싱, `hermes config set gateway.multiplex_profiles true`)로 방향을 틀어 직접 설정해봄.
- **Mattermost 봇별 사용자 필터링 원리 정리**: Mattermost 서버는 멘션/허용목록 필터링을 전혀 안 해주고, 봇 토큰을 쥔 Hermes 게이트웨이가 메시지를 다 받은 뒤 자기 쪽에서 `MATTERMOST_REQUIRE_MENTION`/`MATTERMOST_ALLOWED_USERS`/`MATTERMOST_ALLOWED_CHANNELS`로 스스로 걸러낸다(Slack의 "권한을 좁게 주는" 방식과 다름). `MATTERMOST_ALLOWED_USERS`엔 `@username`이 아니라 26자리 User ID를 넣어야 함.
- **실제 운용 중 버그 발견 및 코드로 확정**: 멀티플렉싱을 켠 상태에서 secondary profile(`second`, 이후 `sandbox`)에 `MATTERMOST_ALLOWED_USERS`를 설정해도 무시되는 현상을 실측(rlaehddus302/test2 2계정으로 재현) → 소스 추적 결과, 멀티플렉싱 모드에서는 프로세스 전역 `os.environ`에 **default profile의 `.env`만** 로드되고 secondary profile의 값은 격리된 secret scope에만 들어가는데, 사용자 인가 함수 `_is_user_authorized`(`gateway/authz_mixin.py`)가 이 scope를 안 읽고 그냥 `os.getenv()`를 써서 **항상 default의 허용목록만 전체 봇에 적용**되는 버그를 확정. 그 결과 "default에 넣은 사람은 모든 봇 통과, 그 외엔 어떤 봇도 통과 못 함"이라는 현상이 재현·확증됨.
- **결론(팀 규모 3명 기준 확정)**: 멀티플렉싱(B)은 프로파일별 Mattermost 사용자 인증이 사실상 안 되므로, **인증이 필요한 profile은 반드시 방법 A(프로파일마다 독립 프로세스: `hermes profile create <name>` → `<name> setup` → `<name> gateway install/run`, 각자 다른 Mattermost 봇 토큰 필수)로 가야 한다**는 결론을 실측으로 재확인. 어제 결론(방법 A 우세)이 자원 소모 우려로 흔들렸으나, 오늘 결국 같은 결론으로 재확정됨.
- 문서화: `experiments/hermes-mattermost/2026-07-10/dongyeon/mattermost-multi-user-mention-setup.md`(오전, Profile A/B 비교·설정법), `experiments/hermes-mattermost/2026-07-10/rlaehddus302/multiplex-mattermost-allowed-users-bug.md`(낮, 버그 코드 근거 정리 + 이후 2계정 실측 확증 섹션 추가) 작성·커밋(`eb6cc01`).

## Mattermost/Hermes 아키텍처 이해 정정 (팀 공유 가치 있음)
- "Hermes가 Mattermost 데이터베이스에 직접 접근해서 과거 기록 전체를 바탕으로 답할 수 있다"는 오해에 대해, 실제로는 **REST/WebSocket API로만 연동**하며 **Mattermost 어댑터에는 히스토리 백필(backfill) 기능이 없어 봇 설치 이전 과거 대화를 소급해서 읽을 수 없다**는 점을 소스로 확인·정정. 세션/기억도 "채널+사용자" 단위로만 쌓임.
- 추가 질문에 "봇이 채널에 있는 동안엔 모든 대화가 다 Hermes로 전달되냐"에 대해, 1차 답은 부정확했고(정정함) 실제로는 `MATTERMOST_REQUIRE_MENTION`(기본 on) 필터가 어댑터 단(`plugins/platforms/mattermost/adapter.py:849`)에서 멘션 안 된 메시지를 그 자리에서 폐기함 — 예외는 DM과 `MATTERMOST_FREE_RESPONSE_CHANNELS` 지정 채널뿐. 즉 채널 전체 맥락을 다 기억하는 게 아니라 멘션된 것만 처리.
- 이 두 확인 사항은 "팀 공유 인텔리전스 레이어(과거 대화 인덱싱·브릿지)를 직접 만들어야 하는 이유"와 직결되는 아키텍처 근거로 정리됨.

## WSL/Docker 환경 트러블슈팅 (개인 환경, 팀 공유 가치 낮음)
- 클립보드 이미지 붙여넣기가 WSL 터미널에서 안 되는 이유(텍스트만 전달 가능, 이미지 바이너리 경로 없음) 확인 — 파일 저장 후 경로 전달 방식으로 대안 제시.
- `VmmemWSL` 메모리 사용량(2GB) 확인 과정에서 Docker Desktop(WSL2 백엔드) 구조 설명, 실제 프로세스별 메모리 사용 확인(`claude` 383MB, `hermes-agent` 게이트웨이 127MB, 나머지는 캐시).
- Mattermost 컨테이너 포트(8065) 충돌 에러 디버깅 — `netstat`으로 포트 점유 PID 확인, Docker Desktop 네트워크 버그로 추정, `wsl --shutdown` 후 재시작 권고.
- 세션 끝 무렵 Hermes 게이트웨이 systemd 서비스 자동시작을 사용자 요청으로 정지+비활성화(`systemctl --user stop/disable hermes-gateway.service`) — 팀 프로젝트와 무관한 개인 로컬 환경 설정.
