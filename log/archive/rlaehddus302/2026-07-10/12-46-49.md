## 검증 요약

멀티플렉싱 모드에서 secondary profile(`second`)의 `MATTERMOST_ALLOWED_USERS`가 무시되는 게 맞고, 원인은 네 단계로 확정됩니다:

1. **`gateway/run.py:1279`** — 게이트웨이 시작 시 전역 `os.environ`에는 **default profile의 `.env`만** 로드됨. second의 `.env`는 절대 안 실림.
2. **멀티플렉싱은 일부러** profile 시크릿을 전역에 안 섞고 격리된 secret scope(contextvar)에만 넣음 (`secret_scope.py`, `run.py:1290-1302`) — 키 유출 방지 설계.
3. **버그 지점**: 사용자 인증 함수 `_is_user_authorized`(`authz_mixin.py:440`)는 그 secret scope를 안 읽고 `os.getenv("MATTERMOST_ALLOWED_USERS")`를 직접 읽음 → 항상 default 값만 봄. (이 파일엔 `get_secret` import 자체가 없음)
4. **게다가** 인증은 profile 스코프가 켜지기 *전에* 실행됨 — 메시지 핸들러(`run.py:8437`)가 스코프 없이 `_handle_message`→인증(`8753`) 호출, 스코프는 인증 통과 후 `_run_agent`(`16466`)에서야 진입.

그래서 님이 보신 `Unauthorized user: jem1... (rlaehddus302)` 로그가 정확히 설명됩니다 — second `.env`에만 ID를 넣었는데 default `.env`엔 없으니, 전역값이 비어서 **기본 거부**로 떨어져 허용하려던 계정이 거부된 겁니다. Mattermost 어댑터는 사용자 인증을 아예 안 하니(멘션/채널 게이팅만) 우회 여지도 없습니다.

**해결**: 인증이 필요한 profile은 멀티플렉싱에서 빼고 독립 프로세스로 돌리는 게 정답입니다(문서에 명령어 정리해뒀습니다). 이건 우리 코드가 아니라 Hermes 상류의 미완성 마이그레이션이라, 운영 우회로 대응하는 게 맞습니다.
