## 1. 메모리 Provider와 Honcho 더 자세히

### 왜 필요한가 — 내장 메모리와의 차이

MEMORY.md/USER.md는 "압축된 요약 노트" 방식이라 설명이 단순합니다. 외부 provider(Honcho 등)는 이보다 **더 정교한 사용자 모델**을 만들고 싶을 때 추가로 붙이는 것입니다. 특히 Honcho는 "이 사람이 어떤 사람인지"를 LLM이 대화 패턴에서 추론해서 계속 갱신하는 방식입니다.

### Honcho의 데이터 구조

- **User Peer(사용자 정체성)** — 워크스페이스 안에서 여러 Hermes 프로필이 공유하는 "이 사람"이라는 하나의 전역 정체성
- **AI Peer(AI 정체성)** — 프로필별로 따로 있음. 예를 들어 "coder" 프로필과 "writer" 프로필은 각각 별도의 AI Peer를 가짐 → 같은 사용자를 보고 있어도, 코딩용 AI는 "이 사람은 최적화를 중요하게 생각함" 같은 코드 중심 관찰을 쌓고, 글쓰기용 AI는 편집 스타일 중심 관찰을 따로 쌓음
- **Representation(사용자 표상)** — 지금까지 관찰된 대화 패턴에서 LLM이 종합한 사용자 프로필 (예: "이 사람은 계속 최적화 질문을 함 → 성능 중심 사고를 하는 사람"으로 요약)
- **Peer Card** — AI Peer의 이력서 같은 것. 역할, 전문 분야, 최근 상호작용 요약
- **Session Summary** — 지금 이 세션에서 무슨 일이 있었는지 압축한 것

### 딜렉틱(dialectic) 추론 — 실제 동작 순서

1. 사용자 메시지가 들어오면, 쿼리 길이를 보고 얼마나 깊게 추론할지 결정
2. **Cold-start**(아직 기반 맥락이 없을 때): "이 사람에 대해 일반적으로 뭘 알고 있지?"라는 질문으로 시작 → 일반적 사용자 사실만 봄
3. **Warm**(이미 세션 맥락이 있을 때): "오늘 나눈 대화에서 어떤 패턴이 보이지?"라는 질문 → 오늘 세션에 한정된 관찰을 봄
4. Pass 1: 자기 검토(방금 낸 관찰이 앞뒤가 맞는지 스스로 점검)
5. Pass 2(설정 시): 상충하는 관찰들을 조정
6. 결과(최대 600자)를 시스템 프롬프트 맨 앞에 붙여넣음

### 비용/깊이를 따로 조절하는 3개 손잡이

- `contextCadence`(기본 1) — 몇 턴마다 기반 맥락(Session Summary+Representation+Peer Card)을 새로고침할지
- `dialecticCadence`(기본 2) — 몇 턴마다 LLM 추론을 실제로 돌릴지
- `dialecticDepth`(기본 1, 최대 3) — 한 번 돌릴 때 몇 단계(cold/warm 선택 → 자기검토 → 조정)까지 갈지

예: 비용을 아끼고 싶으면 `contextCadence: 3, dialecticCadence: 5, dialecticDepth: 1`처럼 새로고침도 뜸하게, 추론도 뜸하게 설정. 반대로 정확도가 중요하면 전부 1로.

## 2. 게이트웨이 — 질문 하나하나에 답

### "채널 내 다른 사람들끼리의 대화도 다 저장하나, 아니면 봇을 부른 것만 저장하나?"

**기본값은 "봇을 부른 것만"입니다.** `require_mention: true`(그룹 채널 기본값)일 때는, 봇을 직접 태그한 메시지만 처리되고, **그 외 채널의 나머지 대화는 세션 기록(transcript)에 안 들어갑니다.** 즉 10명이 있는 슬랙 채널에서 다들 잡담하는 건 원래는 안 보이는 게 기본입니다.

**단, "히스토리 백필(history backfill)"이라는 예외가 있습니다.** 봇이 멘션될 때, "내가 마지막으로 답한 시점부터 지금 멘션된 시점까지" 그 사이 채널에서 오간 메시지를 뒤로 훑어서(Discord 기본 최대 50개) 맥락으로 끌어옵니다. 즉:

- 평소엔 안 보다가
- **멘션당하는 순간**, "아 잠깐, 내가 마지막으로 말한 뒤로 무슨 얘기가 오갔더라?"하고 최근 대화를 스캔해서 참고자료로 씀
- 이건 영구 저장(memory)이 아니라 **그 응답을 만들 때 한 번 쓰는 맥락**에 가깝습니다.

### "메시지를 받아서 → 세션 저장소에 넣고 → AIAgent로 넘겨서 처리 → 응답을 돌려줌"이 뭔 소리냐

10명이 있는 Slack 채널에서 누가 `@bot 안녕`이라고 쳤다고 하면:

1. **Slack 어댑터(플랫폼 연결 담당 코드)**가 그 메시지를 받음
2. 이 메시지를 "이 채널 전용 세션 저장소"에 기록함 (아래에서 설명할 "세션 = 대화방 단위" 개념)
3. 필요하면 히스토리 백필로 최근 맥락도 같이 끌어와서
4. **AIAgent(실제로 답을 생각해내는 LLM 두뇌 부분)**에 "이 세션의 지금까지 기록 + 지금 온 메시지"를 통째로 넘김
5. AIAgent가 답을 만들어내면
6. 다시 Slack 어댑터를 통해 그 채널에 답장을 씀

즉 이건 "웹서버가 요청 받아서 → DB 조회하고 → 비즈니스 로직 처리하고 → 응답 반환"하는 것과 똑같은 패턴이라고 생각하면 됩니다. 플랫폼 어댑터는 "입출력 담당", AIAgent는 "생각하는 부분", 세션 저장소는 "이 대화방의 기억"입니다.

### "대화방"이란 무엇이고, 왜 채널/DM이 각각 독립 세션인가

"대화방(chat)"은 그 플랫폼에서 **메시지가 오가는 하나의 공간 단위**를 말합니다 — Slack이면 채널 하나 또는 DM 하나, Discord면 서버의 특정 채널 하나. 세션은 **사람 단위가 아니라 이 "대화방" 단위**로 나뉩니다.

- **채널 세션**: 그 채널에서 봇을 부른 기록들이 쌓이는 하나의 세션. 채널에 여러 명이 있어도 "그 채널"이라는 하나의 세션에 다 같이 들어감 (누가 말했는지 구분은 되지만 세션 자체는 채널 기준 하나).
- **DM 세션**: 같은 사람이 봇과 1:1로 나눈 대화는 그 사람과의 DM이라는 별도의 대화방이므로, **채널 세션과는 완전히 다른 별개의 세션**입니다.

그래서 예를 들어 제가 `#general` 채널에서 봇에게 뭔가 물어본 기록과, 제가 봇과 개인 DM으로 나눈 기록은 **서로 다른 기억 문맥**으로 취급됩니다 — 채널에서 물어본 걸 DM에서 "아까 그거 뭐였지" 하면 기본적으로는 못 알아듣는다는 뜻입니다(단, 앞서 설명한 session_search로 검색은 가능할 수 있음).

→ **우리 프로젝트 관점에서 중요한 시사점**: TeamBrain이 원하는 "여운호가 채널에서 알아낸 걸 김동연도 안다"는 건, 이 기본 구조(대화방=세션 단위, 멘션 안 하면 기록 안 함)로는 안 되고, 우리가 만드는 "팀 공유 지능 레이어"가 이 경계를 넘어서 정보를 엮어주는 부분이라는 게 다시 한번 확인됩니다.
