1단계 — 부품 3개 직접 만져보기 (이번 주 핵심)

부품 A. Mattermost (담당: 김동연 / 인프라)

"우리가 만들 게 아니라 그냥 설치해서 쓰는 메신저"

1. Docker로 내 컴퓨터에 Mattermost 하나 띄우기 (공식 문서에 docker 한 줄 설치법 있음)
2. 팀 만들고 채널 만들고 그냥 카톡처럼 써보기
3. 봇 계정 하나 만들고, 그 봇의 토큰(비밀번호 같은 열쇠)으로 REST API를 때려서 "채널에 메시지 보내기" 성공시키기

→ 여기까지 되면 @ai 멘션 → 우리 코드가 수신 왕복의 절반이 끝난 거예요.

부품 B. Hermes Agent (담당: 여운호 / AI 엔진)

"우리가 만들 게 아니라 포크해서 심장으로 쓰는 개인 AI 엔진"

1. GitHub에서 hermes-agent 클론(내 컴퓨터로 복사)해서 로컬에서 실행, AI랑 대화해보기
2. 메모리가 실제로 어디에 어떻게 저장되는지 파일/DB를 직접 열어보기 — 지난 대화에서 정리한 3층(영속 사실 로그 / SessionDB / 스킬)이 코드에서 실제로 어떻게 생겼는지 눈으로 확인

→ 이게 7/09 일정의 "메모리 구조 학습"이고, 지난번 얘기한 "1인용 → 팀용 변환"의 난이도를 여기서 판단하게 돼요.

부품 C. Honcho (담당: 여운호+신홍재 / 팀 지능의 뿌리)

"Hermes가 기억·사용자모델링에 쓰는 하부 저장소. 팀 전환의 발판이 여기 있음"

1. Honcho 문서에서 workspace / peer / session 데이터 모델 파악

# Phase 0 — 진짜 기초 (전제 조건, 2~3일 / 이미 되면 스킵)

"아무것도 모른다" 가정이라 깔고 가는 바닥. **이미 할 줄 알면 건너뛰세요.**

| 항목 | 뭘 배우나 | 완료 기준 |
|---|---|---|
| 터미널/셸 | 폴더 이동(`cd`), 목록(`ls`), 파일 보기 정도 | 명령어로 폴더 오가며 파일 열 수 있다 |
| Git 아주 기본 | 커밋(저장 시점 기록)·푸시(공용 저장소에 올리기)가 *뭔지* 개념만 | (실행은 Claude가 대신하니) 용어를 알아듣는다 |
| 프로그래밍 언어 1개 | Python **읽기** 위주 (함수·변수·if·반복문·import) | 남의 Python 코드 보고 "대충 뭐 하는지" 말할 수 있다 |
| HTTP 기본 | 요청/응답, 주소(URL), 상태코드(200=성공, 404=없음) | "이 프로그램이 저 주소로 요청 보낸다"가 그림이 그려진다 |

**학습법**: 이 폴더에서 Claude Code한테 "파이썬 이거 한 줄씩 설명해줘", "HTTP 요청이 뭔지 택배로 비유해줘" 식으로. 책 사지 말고 필요할 때 물어보며 진행.

# Phase 1 — 공용 개념 (전원 공통, 2~3일)

역할 불문 다 알아야 하는 공용어. 깊게 말고 **감만**.

| 개념 | 한 줄 뜻 | 왜 필요 | 완료 기준 |
|---|---|---|---|
| LLM / 토큰 / 컨텍스트 윈도우 | AI가 한 번에 읽는 글 양엔 한계가 있다 | 메모리를 왜 요약·검색하는지 | "왜 다 못 넣고 검색하나"를 설명할 수 있다 |
| 에이전트 & 툴 콜 | AI가 대화만 아니라 도구를 직접 호출해 일한다 | "파일 생성·수정"의 원리 | 멘션→AI가 작업하는 흐름을 그린다 |
| REST API | 요청-응답식 프로그램 대화 | Mattermost 연동 | "요청 보내면 답 온다"를 예로 든다 |
| WebSocket | 계속 연결해 실시간 수신 | 멘션 즉시 받기 | REST와 뭐가 다른지 한 줄로 |
| JSON | 프로그램끼리 쓰는 데이터 표기법 | API 다루면 매 순간 | JSON 하나 보고 값 찾을 수 있다 |
| 봇 계정 / 웹훅 | AI용 메신저 계정 / 이벤트 알림 콜백 | @ai 멘션 처리 | 봇이 왜 필요한지 안다 |
| **프로세스 분리** | 우리 코드는 Mattermost 밖 별도 프로그램 | ★AGPL 라이선스 필수 (PLAN 6-1) | "왜 플러그인으로 넣으면 안 되나"를 말한다 |
| Docker / 컨테이너 | 프로그램을 설정째 담은 실행 상자 | 설치·배포 전부 | "왜 내 PC에 직접 안 깔고 컨테이너로?"를 안다 |

**완료 기준(Phase 전체)**: 팀 회의에서 위 단어들이 나올 때 아무도 못 알아듣는 사람이 없다.

**완료 기준**: "이 AI의 기억이 물리적으로 어느 파일/테이블에 어떤 모양으로 들어가는지"를 팀에 그림으로 설명할 수 있다. (= 7/09 "메모리 구조 학습", 팀→개인 변환 난이도 판단의 근거)

### 부품 C. Honcho — 담당 여운호+신홍재 (팀 지능의 뿌리)
> Hermes가 기억·사용자모델링에 쓰는 하부 저장소. **팀 전환의 발판이 여기 있음**

| 단계 | 하는 일 |
|---|---|
| C-1 | 문서에서 **workspace / peer / session** 데이터 모델 파악 |
| C-2 | ★**1순위 확인**: "한 session에 여러 peer 넣기 되나? peer별 기억 격리되나?" — 스키마 직접 열어 검증 |

**완료 기준**: `팀=workspace, 팀원=peer, 채널=session` 매핑이 **실제로 되는지 안 되는지 답이 나온다.** (이 답이 Phase 3 전체 난이도를 좌우 — 제일 중요)

# Phase 3 — ★붙이는 레이어★ (우리가 만드는 것, 2~4주)

여기가 **진짜 실력 붙는 곳이자, 우리 제품의 오리지널이자, Spring 취업에 남는 부분**이에요. Phase 2를 통과해야 시작 가능 (부품을 모르면 설계 불가). 1→5 순서로, 각 단계는 "제일 작은 걸 실제로 동작"부터.

각 항목: **뭘 배우나 / 최소 목표(MVP 수준) / 완료 기준 / 백엔드 용어**

### 3-1. API 통합 실전
- **뭘 배우나**: 이벤트 수신 → 처리 → 응답 왕복을 실제 코드로. 토큰 인증, 재시도, 에러 처리.
- **최소 목표**: `@ai 안녕` 치면 → 우리 코드가 받아 → Hermes에 넘겨 → 답을 채널에 되돌린다 (그냥 통과만).
- **완료 기준**: 멘션 한 줄이 사람 개입 없이 답으로 돌아온다. (= 7/16 MVP의 심장)
- **백엔드 용어**: REST/WebSocket 클라이언트, 외부 연동

### 3-2. 어댑터 설계
- **뭘 배우나**: "Mattermost 데이터 모양"과 "Hermes/Honcho 데이터 모양"을 서로 번역하는 중간 계층. 관심사 분리(각 코드가 한 가지 일만).
- **최소 목표**: Mattermost 사용자·채널·스레드를 Honcho peer·workspace·session으로 바꾸는 매핑 함수.
- **완료 기준**: Mattermost가 바뀌어도 엔진 쪽 코드는 안 건드리게 "번역기"가 분리돼 있다.
- **백엔드 용어**: 어댑터 패턴, 계층 분리(layered architecture)

### 3-3. 데이터·상태 모델링
- **뭘 배우나**: 메모리 하나하나에 `소유자 / 가시성(개인·팀공유)` 태그 붙이기, "팀 공유 합집합" 뽑는 조회 설계.
- **최소 목표**: 사실 저장 시 `owner`, `visibility` 필드 추가 + "이 사람이 볼 수 있는 것"만 조회하는 쿼리.
- **완료 기준**: 같은 질문을 두 사람이 물으면, 각자 권한에 맞게 다른(또는 공유된) 답이 나온다.
- **백엔드 용어**: 데이터 모델링, 집계 쿼리

### 3-4. 권한·인가 설계 ★ (제일 어렵고 제일 novel)
- **뭘 배우나**: 개인 지식이 팀으로 올라갈 때 거르는 필터, 비밀정보 마스킹(가리기), 접근 제어 규칙.
- **최소 목표**: 규칙 딱 하나부터 — "비공개 채널 대화는 팀 검색에 안 뜬다".
- **완료 기준**: "여운호의 비밀 메모가 김동연 검색에 안 샌다"가 실제로 막힌다.
- **백엔드 용어**: **Authorization(인가) / 접근제어** — 모든 백엔드의 심장. *이 항목이 이력서 스토리의 핵심.*

### 3-5. 시스템 설계
- **뭘 배우나**: 별도 프로세스 분리(라이선스 필수), 여러 팀원 동시 사용 시 상태 관리(동시성), 로깅·테스트.
- **최소 목표**: 우리 레이어가 Mattermost/Hermes와 **다른 프로세스**로 돌고, 두 명이 동시에 멘션해도 안 꼬인다.
- **완료 기준**: 동시에 여러 명이 써도 답이 섞이지 않고, 문제 생기면 로그로 추적된다.
- **백엔드 용어**: 서비스 간 통신, 동시성, 운영

**Phase 3 전체 완료 기준**: "개인 AI 여러 개 + 권한 필터 + 팀 공유 뷰"가 붙어서, **한 명이 알아낸 걸 다른 팀원이 (권한 내에서) 자기 AI로 물어보면 안다.** = 기획서 주요기능 2번 실현.

# 그래서 "코드 짤 일 거의 없나?" — **정반대예요**

이 오해가 자주 생기는데, 정확히 짚을게요:

**우리가 안 짜는 것 (그래서 재발명 안 함):**
- 메신저(Mattermost), 개인 AI 엔진(Hermes), 기억 저장소(Honcho) → 이 셋은 남이 만든 거대한 코드를 **가져다 씀**.

**우리가 짜는 것 (전부 우리 원본 코드):**
- **Phase 3 전체** — 어댑터, 데이터 모델링, **권한·인가**, 시스템 설계. 이건 설정 몇 줄이 아니라 **진짜 백엔드 코드**예요.
- Phase 4 배포 설정, 대시보드 프론트(TypeScript)도 우리 몫.

비유하자면 — **전체 시스템 코드의 양(줄 수)으로 보면 우리가 쓰는 건 10% 남짓**이에요. 나머지 90%는 가져다 쓰는 부품이니까. **하지만 그 10%가 제일 어렵고, 제일 창의적이고, 제일 가치 있는 부분**입니다. "보일러플레이트(반복되는 뻔한 코드)는 줄고, 어려운 핵심 코드에 집중"하는 구조예요.

그리고 이 팀은 그 코드도 **Claude Code에게 지시해서** 만들죠. 그런데 그게 "코드 안 짠다"는 뜻은 아니에요:
- **뭘 만들지 설계**하고 (권한 규칙은 어떻게? 데이터는 어떤 모양으로?)
- **나온 코드를 이해·검수**하고 (이게 맞나? 비밀 새는 구멍 없나?)
- **안 되는 걸 디버깅**하는 건 → 여전히 사람이, 코드를 알아야 합니다.

**결론**: "엔진 안 만든다 ≠ 코드 안 짠다." 오히려 **적게 짜는 대신, 짜는 것마다 어려운 원본 코드**예요. 그리고 그 원본이 몰려 있는 Phase 3이 곧 여러분 실력과 (지난번 얘기한) 백엔드 취업 스토리가 나오는 곳이고요.
