## 전체 그림

```
┌─────────────────────────────────────────────┐
│  Mattermost (순정 설치 · 우리가 소스 수정 안 함)   │  ← 비개발자 접점, 데이터 주권
│   팀원이 채널/DM에서 @ai 멘션으로 대화             │
└───────────────┬─────────────────────────────┘
                │ REST / WebSocket API (공개 API만 사용)
┌───────────────▼─────────────────────────────┐
│  Hermes (MIT 라이선스 → 포크해서 자유롭게 수정)     │  ← 개인 AI 엔진, 재발명 안 함
│   Mattermost 연동 게이트웨이 내장                │
│   개인 학습 루프 · 세션 넘는 기억 · 사용자 모델링    │
└───────────────┬─────────────────────────────┘
                │ 통합 지점 (우리가 설계)
┌───────────────▼─────────────────────────────┐
│  ★ 우리가 만드는 코드 (오리지널, 별도 프로세스) ★    │
│   ① 팀 공유 지능 레이어  ← Hermes에 없는 핵심     │
│   ② 개인 ↔ 팀 지식 접합 (권한·비밀 보호)         │
```

## 층별 상세

**1층 — Mattermost (접점)**
- 팀이 자기 서버에 직접 설치하는 오픈소스 팀 메신저. 우리는 이걸 **절대 수정하지 않고** 순정 그대로 씁니다.
- 이유: Mattermost는 대부분 AGPL v3.0 라이선스라, 소스를 고쳐서 배포/서비스하면 우리가 고친 부분까지 공개해야 하는 의무(AGPL §13, 네트워크 서비스에도 적용)가 생겨요. 그래서 REST/WebSocket 같은 **공개 API로만** 연동합니다.
- 팀원이 채널이나 DM에서 `@ai`를 멘션하면 그게 트리거가 돼서 아래 층으로 이벤트가 전달됩니다.
- 데이터가 전부 이 서버(팀이 소유한 서버)에만 남기 때문에 "데이터 주권"이 확보돼요.

**2층 — Hermes (개인 AI 엔진)**
- MIT 라이선스라서 소스를 자유롭게 포크·수정해서 씁니다 (저작권 고지만 유지).
- Mattermost에 연결하는 게이트웨이가 이미 내장돼 있어서(`MATTERMOST_URL`/`MATTERMOST_TOKEN`만 설정하면 멘션 감지·스레드·채널별 세션 분리까지 기본 지원), 이 연결 코드를 밑바닥부터 새로 짤 필요가 없습니다.
- 개인별 장기 기억(세션이 끝나도 유지), 사용자 모델링(그 사람 성향·자주 쓰는 양식 학습) 같은 기능을 그대로 가져다 씁니다.
- **한계**: 이 내장 게이트웨이는 "멘션한 사람 개인"에게만 응답하는 구조라, 팀 전체가 공유하는 지식(1층 목표)을 만들려면 별도 통합 지점이 필요합니다.
- **개인화 문제**: Hermes의 학습 요약 정보(MEMORY.md/USER.md)는 기본적으로 "프로파일" 단위로만 나뉘고 발신자를 구분하지 않아서, 봇 하나로 여러 사람을 받으면 모두 같은 기억을 공유하게 됩니다. 이걸 풀기 위해 두 가지 방법을 검토했어요:
  - **방법 A (설정만, 코드 불필요)**: 팀원 수만큼 Mattermost 봇 계정을 만들고 각자 다른 Hermes 프로파일에 연결 — MVP 단계에서 채택 예정
  - **방법 B (코드 확장)**: 봇 계정 하나로, Hermes의 "메시지 핸들러 등록" 확장 지점에 우리 코드를 얹어서 발신자 ID로 프로파일을 직접 분기 — 나중 고도화 단계용

**3층 — 우리가 만드는 오리지널 레이어**
- Mattermost·Hermes 어디에도 없는, 이 프로젝트의 진짜 차별화 지점입니다.
- **① 팀 공유 지능 레이어**: 팀원 개개인의 대화·결정을 팀 전체가 쓸 수 있는 지식으로 체계화. 내부적으로 "필터(프라이버시 판별) → 지식 엔진(구조화) → 답변 생성기" 3단계 파이프라인으로 설계 중입니다.
  - 프라이버시 필터는 룰베이스(1차, 키워드/가드레일) + AI 문맥 판별(2차, 애매한 경우) 2단계 구조로 "팀 지식으로 쌓을 대화" vs "개인 프라이버시로 남길 대화"를 가릅니다.
- **② 개인 ↔ 팀 지식 접합**: 권한 관리, 비밀정보 보호 등 두 지식 저장소를 안전하게 연결하는 부분.
- **반드시 별도 프로세스로 돌립니다** — Mattermost의 플러그인 형태로 끼워 넣으면 파생 저작물로 간주될 위험이 있어서, 독립된 프로그램이 공개 API로만 양쪽과 통신하는 구조를 유지합니다.

## 라이선스가 아키텍처를 결정하는 방식

이 프로젝트는 특이하게 **라이선스 제약이 곧 아키텍처 설계 원칙**이에요:
- Mattermost = 손대지 않고 API로만 대화 (AGPL 회피)
- Hermes = 안에 들어가서 마음대로 고침 (MIT라 자유)
- 우리 레이어 = 완전히 독립된 프로세스, 100% 우리 IP

이 원칙만 지키면 순정 Mattermost를 호스팅해서 파는 SaaS 모델도 법적으로 문제없다는 게 PLAN.md Phase 6의 결론이고, 지금 README 열린 질문에도 이 방향(오픈소스+호스팅 vs 자체 메신저 개발)을 멘토님께 재확인하는 항목을 넣어뒀어요.
