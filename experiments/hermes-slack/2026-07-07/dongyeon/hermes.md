# Hermes 공부본 (dongyeon)

NousResearch/hermes-agent(MIT)를 완전 처음부터 공부하면서 정리한 노트.
공식 문서(hermes-agent.nousresearch.com/docs)를 기반으로 함.
TeamBrain(PLAN.md) 아키텍처에서 Hermes는 "개인 학습 에이전트" 엔진 역할.

---

## 1. Hermes가 뭐 하는 물건인가

한 줄 정의: **세션이 끝나도 리셋되지 않고, 쓸수록 기억이 쌓이고 스스로 노하우
(스킬)를 만들어가는 자율 AI 에이전트.** 특정 IDE에 묶인 코딩 코파일럿도
아니고, 하나의 API를 감싼 챗봇 래퍼도 아니라고 스스로 규정함.

핵심 축 4가지:

1. **게이트웨이** — 여러 메신저(Slack/Discord/Telegram/Mattermost 등)에 연결
2. **메모리** — MEMORY.md/USER.md(요약) + 전체 대화 원문 검색(session_search)
3. **스킬** — 절차 노하우를 스스로 만들어 재사용
4. **도구/자동화** — 터미널 실행, 크론, 서브에이전트 등 (우리 프로젝트엔 당장 불필요)

---

## 2. 설치 & 첫 실행

```bash
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
```
Python/Node.js/ripgrep/ffmpeg 등 의존성, 레포 클론, 가상환경, 전역 `hermes`
명령어까지 스크립트가 알아서 세팅. 그다음 `hermes setup`으로 LLM(대화 엔진)
공급자를 고름 (3번 항목 참고).

```bash
hermes          # 클래식 CLI
hermes --tui    # 터미널 UI (권장)
hermes doctor   # 설치/설정 진단
```

## 3. LLM 공급자 설정 — Nous Portal이 뭔지

`hermes setup` 실행 시 고르는 방식:

- **Quick Setup (Nous Portal)** — OAuth 로그인만으로 바로 씀
- OpenRouter / OpenAI / 커스텀 엔드포인트 — 직접 API 키 입력

### Nous Portal의 정체

Nous Research가 자체적으로 만든 LLM이 **아니다.** 실제로는 뒤에서
**OpenRouter를 통해 Claude, GPT, Gemini, DeepSeek, Qwen 등 다른 회사들의
진짜 프론티어 모델**에 연결해주고, 사용료를 "Nous 구독" 하나로 묶어서
청구해주는 **결제/라우팅 대행 서비스**. 여러 회사 API 키를 따로 안 만들어도
`/model anthropic/claude-sonnet-4.6` 처럼 모델을 골라 쓸 수 있게 해줌.

### 비용

- OAuth **로그인 자체는 무료**지만, 실제 모델 사용은 **유료 Nous 구독이
  필요**함 (공식 문서에 구체적 가격표는 없고, portal.nousresearch.com에서
  구독 관리). "무료"라는 건 로그인 방식이 쉽다는 뜻이지, 모델 사용까지
  공짜라는 뜻은 아님.

### Claude/Gemini를 Hermes에 연결해도 되나? (약관 문제)

연결 방식에 따라 완전히 다름:

- **정식 API 키(종량제 결제)로 연결** — 문제없음. Anthropic/Google이 API를
  만든 목적 자체가 이런 프로그램 연동임. Nous Portal도 결국 OpenRouter를
  거쳐 이 정식 경로로 붙는 것이라 안전함.
- **개인 웹 구독 로그인(claude.ai Pro 계정 등)을 비공식적으로 API처럼
  재활용하는 것** — 이건 실제 약관 위반이고, 계정 정지 사례가 있음.

→ **주의**: PLAN.md Phase 8의 "초기 유저는 Claude/Codex 등 유료 구독
보유자 위주라 비용 부담이 적다"는 가정이, 만약 "유료 구독"을 웹 구독 계정
재활용으로 해석한 거라면 이 위험한 쪽에 해당할 수 있음. 정식 API 키
결제와는 다른 문제라 실제 구현 전에 팀/멘토와 한 번 짚고 넘어갈 필요 있음.

## 4. 게이트웨이 — 메신저 연결 구조

**게이트웨이 = 백그라운드 프로세스 하나가 설정해둔 모든 메신저 플랫폼에
동시에 연결되어 있는 구조.** 플랫폼마다 봇을 따로 띄우는 게 아님.

### 메시지 처리 흐름 (예: Slack 채널에서 `@bot 안녕`)

1. Slack 어댑터(플랫폼 연결 코드)가 메시지를 받음
2. 그 **채널 전용 세션 저장소**에 기록
3. AIAgent(실제 두뇌, LLM)에 "이 세션 기록 + 지금 메시지"를 넘김
4. AIAgent가 응답 생성
5. 다시 Slack 어댑터를 통해 그 채널에 답장

→ 웹서버로 치면 "요청 받기 → DB 조회 → 로직 처리 → 응답 반환"과 같은 패턴.

### 세션(session) 단위 — 대화방 + 사람 조합이 기본값

- 대화방 = 그 플랫폼에서 메시지가 오가는 공간 하나 (채널 하나, DM 하나)
- **그룹/채널 세션은 기본적으로 "대화방 + 그 안의 사람"으로 나뉨**
  (`group_sessions_per_user` 기본값 true). 즉 같은 채널 안에서도 사람마다
  기억이 따로 격리됨 — "채널 하나 = 공용 세션 하나"가 아님. 채널 전체가
  하나의 세션을 공유하게 하려면 이 설정을 명시적으로 꺼야 함
- 반대로 **스레드(thread)는 기본이 "공유" 세션**이라, 켜고 끄는 방향이
  채널과 반대라 헷갈리기 쉬움
- 같은 사람이어도 **채널 세션과 DM 세션은 완전히 별개** — 채널에서 물어본
  걸 DM에서 "아까 그거 뭐였지" 하면 기본적으로 못 알아들음
- **플랫폼을 넘어가면 세션이 이어지지 않음** — Telegram에서 얘기하다
  Discord로 옮기면 완전히 새 세션. 플랫폼 간 통합 사용자 식별 장치 없음
  (허용목록도 `TELEGRAM_ALLOWED_USERS`, `DISCORD_ALLOWED_USERS`처럼
  플랫폼별로 따로 관리됨)

### 그룹 채널에서 "누가 뭘 봤는지" — 기본은 멘션한 것만

`require_mention: true`(그룹 채널 기본값)일 때, **봇을 직접 태그한 메시지만
처리되고 세션 기록에 남음.** 채널의 다른 잡담은 원래는 안 보임.

단, **히스토리 백필(history backfill)**이라는 예외 기능이 **Discord와
Telegram에는** 있음: 봇이 멘션되는 순간, "내가 마지막으로 답한 뒤로 무슨
얘기가 오갔나"를 최근 대화 기준으로 뒤로 훑어서(Discord 기본 최대 50개)
그 응답을 만들 때 맥락으로 한 번 끌어옴. 이건 영구 저장이 아니라 그 순간의
참고자료에 가까움. **Mattermost 어댑터에는 이 기능이 구현되어 있지 않음**
— 필요하면 우리가 별도로 만들어야 함.

### 접근 제어

- **허용목록(allowlist)**: 환경변수로 "이 사람들만 말 걸 수 있음" 지정
- **관리자/일반 분리**: 전체 권한 vs 제한된 명령 실행 권한
- **DM 페어링**: 모르는 사용자는 일회용 코드로 인증
- `/platform` 명령으로 모든 어댑터 상태 확인, 반복 실패 시 자동 일시정지

### Mattermost는 이미 지원됨

Hermes는 이미 Mattermost용 게이트웨이를 내장(REST API v4 + WebSocket,
`MATTERMOST_URL`/`MATTERMOST_TOKEN` 환경변수로 설정). Slack과 동일한
require_mention/스레드/DM 구조를 그대로 쓰되, 히스토리 백필 기능은 없음
(위 §4 참고).

→ **우리 프로젝트 시사점**: PLAN.md의 "① Mattermost 어댑터"를 완전히
밑바닥부터 새로 안 짜도 될 가능성 있음. 다만 이 기본 구조로는 "여운호가
채널에서 알아낸 걸 김동연 AI도 안다"는 **팀 간 지식 공유(② 팀 공유 지능
레이어)**는 안 됨 — 세션이 대화방/멘션 단위로 격리돼 있기 때문. 이 격리를
넘어 정보를 엮는 게 바로 우리가 새로 만들어야 하는 부분. (기존 어댑터를
포크해서 플러그인/이벤트 훅으로 팀 레이어를 끼워 넣을지, 아니면 직접 얇은
어댑터를 새로 짤지는 8월 재결정 사항으로 남겨둠 — PLAN.md Phase 8 참고.)

## 5. 메모리 — 2단계 구조

### 계층 1: MEMORY.md / USER.md — 압축 요약 (항상 켜져 있음)

저장 위치: `~/.hermes/memories/`

- **MEMORY.md** (~2,200자/800토큰): 에이전트 메모 — 환경 사실, 프로젝트
  컨벤션, 도구 특이사항, 완료 작업, 배운 요령
- **USER.md** (~1,375자/500토큰): 사용자 프로필 — 이름, 역할, 시간대,
  소통 스타일, 업무 습관, 기술 수준

**동작 방식**:
- 세션 시작 시 두 파일이 시스템 프롬프트에 통째로 주입됨 (`§`로 항목 구분,
  사용률 % 표시)
- 이 스냅샷은 **세션 시작 때 한 번만 캡처되고 대화 중엔 안 바뀜** (LLM
  프리픽스 캐시 성능 유지 목적) — 대화 중 수정해도 디스크엔 바로 반영되지만
  프롬프트엔 다음 세션부터 반영
- `memory` 도구는 **add / replace / remove** 3가지 동작만 있음. 읽기
  전용 조회 명령은 따로 없음(자동으로 프롬프트에 있으니까)

**뭘 저장하고 뭘 버리는가**:
- 저장: 사용자 선호, 환경 사실, 교정/우회법, 프로젝트 컨벤션, 완료 작업(날짜
  포함), 명시적 요청
- 버림: 사소한 정보, 검색하면 나오는 사실, 대용량 데이터/코드/로그 덤프,
  세션 한정 임시 경로, 이미 다른 컨텍스트 파일에 있는 내용

**용량 초과 시**: 자동으로 오래된 걸 안 지움. 초과하면 `memory` 도구가
에러를 반환하고 현재 항목을 보여줌 → 에이전트가 같은 턴에서 합치거나
지운 후 재시도해야 함. 권장: 80% 이하 유지.

**why 2,200자밖에 안 되는데 세션을 초월해 기억하나?** →
이 파일들은 "전체 기억의 그릇"이 아니라 **매번 자동으로 떠먹여주는 압축
요약본의 그릇 크기**일 뿐. 진짜 방대한 기억은 계층 2(session_search)에
쌓임. 비유: MEMORY.md/USER.md = 책상 위에 항상 펴놓은 요약 노트,
session_search = 서고에 꽂혀있는 전체 회의록.

### 계층 2: session_search (FTS5) — 전체 대화 원문 아카이브

- `~/.hermes/state.db` (SQLite)에 **모든 대화 원문**이 그대로 저장됨
  (용량 제한 사실상 없음 — 디스크 용량만큼)
- 세션 시작 시 통째로 프롬프트에 넣는 게 아니라, **필요할 때만**
  `session_search` 도구로 키워드 검색(FTS5)해서 관련 부분만 불러옴

**저장 크기 걱정 안 해도 됨**:
- 수백 세션 쌓여도 보통 10~15MB, 6개월 정상 사용 시 20~100MB 정도
  (텍스트라 원래 가벼움; 이미지/파일 첨부·도구 로그가 많으면 더 커질 수
  있음)
- 자동 정리: `~/.hermes/config.yaml`에서 `sessions.auto_prune: true`
  (기본 false), `retention_days: 90`(끝난 세션만 90일 후 삭제, 진행 중
  세션은 절대 안 지움), `vacuum_after_prune: true`(삭제 후 디스크 공간
  실제 회수)
- 수동: `hermes sessions prune` / `delete <id>` / `archive`

### 그룹 채널 메시지 기록 여부 (4번 게이트웨이 항목과 연결)

기본은 "봇을 부른 것만" 기록(§4 참고). 채널의 다른 사람들 잡담은 원래
세션 기록에 안 들어가고, 멘션 순간의 히스토리 백필로만 잠깐 참고됨.

## 6. 외부 메모리 Provider & Honcho

### 왜 필요한가

MEMORY.md/USER.md(내장)로도 세션 초월 기억은 되지만, **더 정교한 사용자
모델링**을 원하면 외부 provider를 추가로 붙일 수 있음. **한 번에 하나만**
활성화 가능하고, 내장 메모리는 항상 별개로 계속 켜져 있음.

종류: Honcho, OpenViking, Mem0, Hindsight, Holographic(로컬 SQLite,
무료·오프라인 옵션), RetainDB, ByteRover, Supermemory, Memori 등 9종.

### Honcho — 딜렉틱(dialectic) 사용자 모델링

**데이터 구조**:
- **User Peer**: 워크스페이스 안에서 여러 Hermes 프로필이 공유하는 하나의
  전역 사용자 정체성
- **AI Peer**: 프로필별로 별도 존재 (예: "coder" 프로필과 "writer" 프로필은
  같은 사용자를 보고도 서로 다른 관찰을 쌓음)
- **Representation**: 대화 패턴에서 LLM이 종합한 사용자 프로필 (예: "계속
  최적화 질문 → 성능 중심 사고")
- **Peer Card**: AI Peer의 이력서 같은 압축 요약
- **Session Summary**: 이번 세션 요약

**딜렉틱 추론 단계**:
1. 쿼리 길이 보고 추론 깊이 결정
2. **Cold-start**(기반 맥락 없음): "이 사람에 대해 일반적으로 뭘 아나?"
3. **Warm**(기반 맥락 있음): "오늘 대화에서 어떤 패턴이 보이나?"
4. Pass 1: 자기 검토(관찰 일관성 점검)
5. Pass 2(설정 시): 상충 관찰 조정
6. 결과(최대 600자)를 시스템 프롬프트 맨 앞에 삽입

**비용/깊이 조절 손잡이 3개** (서로 독립적):
- `contextCadence`(기본 1): 몇 턴마다 기반 맥락(Session Summary+
  Representation+Peer Card) 새로고침
- `dialecticCadence`(기본 2): 몇 턴마다 LLM 추론을 실제로 돌릴지
- `dialecticDepth`(기본 1, 최대 3): 한 번에 몇 단계(cold/warm 선택→자기
  검토→조정)까지 갈지

예: 비용 절약형 `contextCadence:3, dialecticCadence:5, dialecticDepth:1`
/ 정확도 중시형은 전부 낮은 숫자(자주 새로고침·자주 추론).

## 7. 스킬(Skills) — 절차 기억

메모리가 "사실/선호"라면, 스킬은 **"이 일은 이렇게 하면 된다"는 노하우
문서**.

- 저장 위치: `~/.hermes/skills/` (설치 시 기본 번들 스킬 복사됨: ascii-art,
  arxiv 검색, github PR 워크플로우, plan 모드, excalidraw 등)
- **점진적 공개(progressive disclosure)**: 목차만 항상 프롬프트에 두고,
  실제 내용은 필요할 때만 로드 → 토큰 절약
- 에이전트가 어려운 문제를 풀면 **스스로 스킬 문서를 써서 저장**, 다음에
  재사용. `/skills browse`, `/skills search`로 탐색 가능, Hub에서 남의
  스킬 설치도 가능
- `agentskills.io` 공개 표준 준수 → Hermes 전용이 아니라 다른 에이전트
  도구와도 호환
