## 팀 협업 지능 레이어 — 설계 초안

### 1. 데이터 흐름 3단계
```
[캡처] Mattermost 이벤트 (멘션 응답, 스레드, 채널 메시지)
   ↓
[추출·정제] 우리 레이어가 "지식 단위"로 가공 (비동기)
   ↓
[저장·색인] 팀 지식 저장소 (임베딩 + 구조화 메타데이터)
   ↓
[검색·주입] 다음 @ai 호출 시 관련 지식을 컨텍스트로 불러와 응답에 반영
```

### 2. "지식 단위(Knowledge Unit)"를 뭘로 정의할지가 핵심
모든 대화를 통째로 저장하면 그냥 로그고, 그러면 이 레이어를 만들 이유가 없음. 대화에서 **재사용 가치 있는 단위**를 뽑아내야 함. 후보 taxonomy:

- **결정(Decision)** — "우리 이거 A로 하기로 함" (근거·날짜·누가 포함)
- **사실/노하우(Fact)** — "이 API는 rate limit이 시간당 100회다" 같은 재사용 가능한 정보
- **미해결 이슈(OpenQuestion)** — 아직 답 안 난 것 (Phase 8처럼)
- **용어/정의(Glossary)** — 팀 안에서만 통하는 약어·용어

각 단위는 `출처 스레드 링크 + 채널 + 작성자 + 타임스탬프 + 신뢰도(합의됐는지 vs 한 사람 의견인지)`를 메타데이터로 가짐.

### 3. 추출은 언제, 어떻게 트리거되나
- 실시간 추출(멘션마다)은 비용·노이즈 과다 → **스레드가 "닫힐 때"(일정 시간 무응답 또는 명시적 신호) 배치로 요약·추출**하는 게 현실적
- 또는 팀원이 명시적으로 `@ai 이거 기억해` 같은 커맨드로 강제 등록 (초기엔 이게 더 신뢰도 높고 구현 쉬움)
- MVP는 후자(명시적 등록)로 시작하고, 검증되면 자동 추출을 얹는 순서를 제안

### 4. 팀 지식 vs 개인 지식(Hermes)의 경계
- Hermes는 "이 사람이 어떻게 일하는지, 무슨 스타일을 좋아하는지" 같은 **개인 모델링**
- 팀 레이어는 "팀이 뭘 결정했고 뭘 아는지" 같은 **공유 사실**
- 브릿지 규칙: 개인 DM에서 나온 내용은 기본적으로 팀 지식으로 승격 안 됨(권한 문제, CLAUDE.md의 "개인↔팀 브릿지·비밀정보 관리" 원칙과 일치). 채널(공개) 대화만 팀 지식 후보.

### 5. 검색·주입 (응답 생성 시점)
`@ai` 멘션 → ① 개인 Hermes 기억 조회 + ② 팀 지식 저장소에서 관련 Knowledge Unit 검색(임베딩 유사도 + 채널 권한 필터) → 두 결과를 합쳐 프롬프트에 주입 → 응답.
