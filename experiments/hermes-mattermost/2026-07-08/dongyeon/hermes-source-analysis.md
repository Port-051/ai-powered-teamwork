## 1. 메시지 하나가 처리되는 전체 흐름

Hermes는 하나의 프로그램(백그라운드 프로세스)이 여러 메신저(Slack, Discord, Telegram,
Mattermost 등)에 동시에 연결되어 있는 구조다. 플랫폼마다 봇을 따로 켜는 게 아니라, 프로그램
하나 안에 "메신저별 연결 담당자(어댑터)"가 여러 명 들어있는 것에 가깝다.

메시지 하나가 들어와서 답장이 나가기까지 다음 순서를 거친다:

1. **플랫폼 어댑터가 메시지를 받는다.** 예를 들어 Mattermost는 `plugins/platforms/mattermost/adapter.py`라는
   파일이 이 역할을 한다. 이 어댑터는 두 가지 방법으로 Mattermost 서버와 통신한다:
   - REST API(정해진 주소로 요청을 보내고 답을 받는 방식) — 메시지를 보낼 때, 채널 정보를
     조회할 때 등에 사용
   - WebSocket(연결을 계속 열어두고 실시간으로 이벤트를 주고받는 방식) — 새 메시지가
     올라올 때마다 실시간으로 알림을 받기 위해 사용
2. **"이 메시지를 봇이 반응해야 하는 메시지인가?"를 판단한다.** (아래 2번 항목에서 자세히 설명)
3. **어떤 "기억 상자(세션)"에 이 메시지를 넣을지 정한다.** (아래 3번 항목에서 자세히 설명)
4. **AIAgent(실제 두뇌 역할, LLM 호출을 포함한 로직 전체)에게 "지금까지의 대화 기록 + 방금
   온 메시지"를 넘긴다.** 이 부분은 모든 메신저 어댑터가 공통으로 사용하는 코드
   (`gateway/platforms/base.py`)를 거친다 — 즉 어느 메신저로 들어왔든 이 지점부터는 같은
   방식으로 처리된다.
5. **AIAgent가 답을 만든다.** 이 과정에서 필요하면 도구(메모리 조회/저장, 과거 대화 검색,
   스킬 문서 읽기 등)를 사용하고, 실제 LLM(예: Claude, GPT 등) 호출도 여기서 일어난다.
6. **다시 원래 어댑터를 통해 그 메신저로 답장을 보낸다.**

비유하자면, 여러 창구(메신저 어댑터)가 있는 은행 건물 하나가 있고, 어떤 창구로 들어와도
결국 뒤쪽의 같은 처리 부서(AIAgent)로 서류가 넘어가서 처리된 뒤, 다시 원래 들어온 창구로
결과가 나가는 구조와 비슷하다.

## 2. "봇을 불러야만 반응한다"는 규칙이 어떻게 동작하는가

단체 채팅방(그룹 채널)에서는 사람들이 나누는 모든 대화에 봇이 다 반응하면 시끄럽기 때문에,
기본적으로 **봇을 직접 태그(멘션)한 메시지에만 반응**하도록 되어 있다. 이 규칙을 켜고 끄는
설정이 `require_mention`이다.

주목할 점은, 이 "멘션 확인 로직"이 메신저마다 **각자 따로 코드로 구현**되어 있다는 것이다.
하나의 공통 함수가 모든 메신저에 똑같이 적용되는 게 아니라, Mattermost는 Mattermost 나름의
방식으로, Slack은 Slack 나름의 방식으로 "이 메시지에 우리 봇 이름이 언급됐나?"를 확인한다.
Mattermost의 경우 환경변수(프로그램 실행 시 설정해두는 값) `MATTERMOST_REQUIRE_MENTION`으로
이 규칙 자체를 켜거나 끌 수 있다.

그리고 일부 메신저(Discord, Telegram)에는 "봇이 멘션되는 바로 그 순간, 자신이 마지막으로
답장한 뒤로 채널에서 오간 대화들을 최근 기록에서 한 번 훑어와서, 지금 답변을 만들 때 참고
자료로 슬쩍 끼워 넣는" 기능이 있다. 예를 들어 채널에서 사람들이 한참 대화를 나누다가 누군가
갑자기 봇을 불러서 "방금 그 얘기 정리해줘"라고 하면, 봇이 "방금 그 얘기"가 뭔지 그 순간에
한해 참고할 수 있게 해주는 보완 장치다. 다만 이건 대화 기록에 영구적으로 남는 게 아니라,
그 답변을 만드는 순간에만 잠깐 불러와서 쓰는 임시 참고자료에 가깝다. 그리고 이 기능은
메신저마다 있고 없고가 다르다 — 모든 메신저에 공통으로 있는 기본 기능이 아니라, 특정
메신저 어댑터에만 따로 구현되어 있는 부가 기능이다.

## 3. 기억이 어떤 단위로 나뉘는가 (세션 구조)

Hermes에서 "세션"이란 봇이 대화 기록을 저장하는 하나의 독립된 상자를 말한다. 이 상자를
어떤 기준으로 나눌지가 세션 키(session key)를 만드는 로직으로 정해지는데, 이 로직에는
몇 가지 조절 가능한 옵션이 있다.

- **1대1 메시지(DM)**: 대화 상대방 한 명당 상자 하나. 어렵지 않은 구조다.
- **단체 채팅방(그룹/채널)**: 기본 설정에서는 **"채팅방 + 그 안에서 말을 건 사람"의 조합으로
  상자가 나뉜다.** 즉 같은 채널 안이라도 사람마다 별도의 상자가 만들어지는 것이 기본값이다.
  이 동작은 `group_sessions_per_user`라는 설정으로 조절 가능하며, 이 값을 끄면 채널 하나
  전체가 상자 하나를 공유하는 방식으로 바뀐다.
- **스레드(하나의 메시지에 달린 답글 묶음)**: 반대로 기본값이 "공유"다. 즉 스레드 안에서는
  누가 말하든 기본적으로 같은 상자를 쓰고, 사람별로 나누려면 별도 설정을 켜야 한다. 채널과
  스레드가 서로 반대 방향의 기본값을 갖고 있어서 헷갈리기 쉬운 부분이다.
- **플랫폼을 넘나드는 경우**: Telegram에서 나눈 대화와 Discord에서 나눈 대화는 완전히 별개의
  세션이다. 플랫폼을 통합해서 "이 사람은 어디서든 같은 사람"이라고 인식하는 장치는 없다.
  허용목록(누가 봇에게 말을 걸 수 있는지 정하는 목록)도 플랫폼마다 따로 관리된다.

정리하면, 세션은 "대화방 하나 = 상자 하나"보다는 좀 더 잘게, "대화방 + 사람"의 조합으로
나뉘는 것이 기본이라고 이해하면 된다. 이 기본값을 그대로 쓸지, 채널 단위로 합칠지는 우리가
팀 지식 공유 레이어를 설계할 때 함께 결정해야 하는 부분이다.

## 4. Hermes를 외부에서 건드리는 세 가지 방법과 그 차이

우리 프로젝트는 "Hermes 소스 코드 자체는 절대 고치지 않고, Hermes 안에 플러그인 형태로
끼워 넣지도 않으며, 완전히 독립된 별도 프로그램으로 우리 코드를 실행한다"는 규칙을 지켜야
한다 (라이선스 문제 때문). 이 기준으로 Hermes가 제공하는 확장 방법들을 살펴봤다.

**방법 A — 플러그인(plugins 폴더)**: Hermes 본체 프로그램 안에 같이 설치되어 함께 실행되는
추가 기능들이다 (스포티파이 연동, 메모리 관련 기능, 이미지 생성 등 다양한 기능이 이 방식으로
들어있다). 메신저 어댑터들(Mattermost 포함)도 사실 이 플러그인 형태로 구현되어 있다. 이
방식은 Hermes와 **같은 프로그램 안에서 함께 실행**되기 때문에, 우리가 지켜야 하는 "완전히
별도 프로그램"이라는 규칙에는 맞지 않는다.

**방법 B — Hook(이벤트 감지) 시스템**: Hermes가 특정 시점(대화 시작/종료, 세션 시작/종료
등)에 "이런 일이 일어났다"는 신호를 보내면, 미리 등록해둔 반응 코드가 자동으로 실행되는
구조다. 소스 코드 자체를 고치지는 않지만, 이 반응 코드 역시 Hermes 프로그램과 **같은
프로세스 안에서 함께 동작**한다. 그래서 이것도 "별도 프로그램" 요건에는 맞지 않는다.

**방법 C — 외부 API 서버 (가장 중요한 발견)**: Hermes 안에는 `api_server.py`라는 기능이
있는데, 이건 Hermes 프로그램이 자기 컴퓨터의 특정 통신 포트를 하나 열어두고 "외부에서 정해진
형식으로 요청을 보내면 답을 해주겠다"는 창구 역할을 하는 것이다. 이 창구는 일반적으로 널리
쓰이는 OpenAI API 형식과 호환되도록 만들어져 있어서, 외부 프로그램이 "이 사람 대화 좀
이어가줘", "이 세션 목록 보여줘" 같은 요청을 표준화된 방식으로 보낼 수 있다. 접근 시에는
별도의 인증 키로 보안을 건다.

이 방법의 장점은, **Hermes 프로그램을 원래 모습 그대로 하나도 안 고치고 그냥 실행해두기만
하면 된다는 것**이다. 우리가 만드는 팀 지식 공유 프로그램은 완전히 독립적으로 실행되면서,
이 창구를 통해 "필요할 때 요청을 보내는" 방식으로만 Hermes와 소통하면 된다. 이는 Hermes
소스를 고치지도, 플러그인으로 끼어 들어가지도 않는 방식이라, 우리가 지켜야 하는 라이선스
규칙(완전히 분리된 별도 프로그램, 공식적으로 공개된 통로만 사용)에 가장 깔끔하게 들어맞는다.

## 5. 기억(메모리) 시스템의 실제 동작 방식

Hermes의 기억은 두 층으로 나뉜다.

**첫 번째 층 — 항상 켜져 있는 요약 메모**: `MEMORY.md`(에이전트가 스스로 남기는 메모, 환경
정보나 작업 습관 같은 것)와 `USER.md`(사용자에 대한 정보 요약)라는 두 파일이 있다. 각각
용량 제한이 있고(대략 2,200자, 1,375자 수준), 대화가 시작될 때 이 두 파일의 내용이 봇의
"머릿속"(시스템 프롬프트)에 통째로 미리 입력된다. 중요한 점은, **이 내용이 대화 시작
시점에 한 번 고정되어 들어가고, 대화가 진행되는 도중에는 실시간으로 갱신되어 반영되지
않는다**는 것이다 (디스크에 있는 실제 파일은 바로 갱신되지만, 그게 지금 하고 있는 대화에
즉시 반영되지는 않고 다음 대화부터 반영된다). 이렇게 만든 이유는 매번 다시 만들지 않고
재사용함으로써 처리 속도와 비용을 아끼기 위함으로 보인다.

이 메모를 관리하는 방법은 딱 세 가지 — 추가(add), 교체(replace), 삭제(remove) — 뿐이다.
읽어보는 명령은 따로 없는데, 어차피 항상 프롬프트에 포함되어 있어서 필요 없기 때문이다.
용량이 꽉 찬 상태에서 새 내용을 추가하려고 하면, 시스템이 오래된 걸 알아서 지워주는 게
아니라 **에러를 돌려주면서 "먼저 기존 내용을 합치거나 지운 다음 다시 시도하라"고 요구**한다.
즉 정리하는 책임은 항상 봇 자신에게 있다.

**두 번째 층 — 전체 대화 원문 저장소**: 위의 요약 메모와 별개로, 나눈 대화 전체가 그대로
작은 데이터베이스(SQLite)에 보관된다. 이건 매번 통째로 불러오는 게 아니라, 필요할 때
검색어로 찾아보는 방식(전문 검색 기능, FTS5)으로 쓰인다. 흥미로운 점은 한국어·중국어·일본어처럼
띄어쓰기가 명확하지 않은 언어의 검색 정확도를 높이기 위한 별도의 검색 방식도 마련되어 있다는
것이다 — 한국어로 대화가 오가는 우리 팀 환경에 유리하게 작용할 수 있는 부분이다.

## 6. 스킬(노하우 문서) 시스템의 실제 동작 방식

스킬은 "이런 종류의 일은 이렇게 처리하면 된다"는 절차적 노하우를 담은 문서다. 매번 모든
스킬의 전체 내용을 봇의 머릿속에 다 넣어두면 비효율적이기 때문에, 두 단계로 나뉘어 있다:

- 짧은 **목차용 설명 파일**(스킬마다 하나씩, 이름과 한두 줄 설명 정도)은 항상 봇의 머릿속에
  포함되어 있다.
- 실제 상세 내용이 담긴 **본문 파일**은 봇이 "이 스킬이 필요하다"고 판단했을 때만 그때
  불러와서 읽는다.

이렇게 하면 평소에는 "이런 스킬들이 있다"는 목록만 가볍게 들고 있다가, 실제로 필요한
순간에만 무거운 본문을 불러오는 식으로 처리량을 아낄 수 있다.

또한 봇은 스스로 새로운 스킬 문서를 써서 저장하는 기능을 갖고 있다. 어려운 문제를 한 번
해결하고 나면, 그 과정을 절차 문서로 정리해서 다음에 비슷한 일이 생겼을 때 재사용할 수 있게
만드는 것이다. 이때 새로 만든 문서가 형식을 제대로 갖췄는지, 크기가 적절한지, 보안상 문제가
없는지를 자동으로 검사하는 절차도 함께 마련되어 있다.

## 7. "대화 기록"과 "학습된 기억"은 서로 다른 저장소이고, 나뉘는 기준도 다르다

3번에서 확인한 세션 구조 때문에 "대화 기록이 채널+사람 조합으로 잘 나뉘니까, 그 위에서
만들어지는 학습 정보(MEMORY.md/USER.md)도 당연히 사람별로 나뉘어 있겠지"라고 생각하기
쉽다. 코드를 더 파본 결과, **실제로는 그렇지 않다.**

5번에서 설명한 기억의 두 층 중, 사람별로 나뉘는 건 **두 번째 층**(전체 대화 원문이 쌓이는
SQLite 저장소)뿐이다. **첫 번째 층**, 즉 "이 사람은 이런 성향이다", "이런 걸 좋아한다" 같은
요약된 학습 정보를 담는 `MEMORY.md`/`USER.md`는 구조가 완전히 다르다:

- 이 파일을 관리하는 `MemoryStore`라는 코드는 어떤 대화방에서 왔는지, 누가 보낸 메시지인지
  같은 정보를 아예 넘겨받지 않는다. 대화방 정보나 사용자 정보를 저장 경로 결정에 쓸 방법
  자체가 코드 구조상 없다.
- 대신 이 저장 경로는 "프로파일(profile)"이라는, 사람이 아니라 **관리자가 미리 정해둔
  설정 단위**에 묶여 있다. Hermes 프로그램이 매 메시지마다 새로 만드는 처리 단위(하나의
  `AIAgent` 인스턴스)는 세션 ID·사용자 ID·플랫폼 정보를 받아서 "대화 기록을 어디에 쌓을지"는
  정확히 알지만, 그 정보가 "학습 요약을 어디에 쓸지" 쪽으로는 전혀 연결되지 않는다.
- 그 결과, 같은 Hermes 프로그램(같은 프로파일) 안에서는 **누가 말을 걸든 상관없이 똑같은
  `MEMORY.md`/`USER.md` 파일 하나**를 읽고 쓰게 된다.

정리하면: "대화 내용이 오간 기록"은 사람별 상자에 나뉘어 저장되지만, 그 대화에서 추출한
"이 사람에 대한 학습 요약"은 그 대화가 어느 상자에서 왔는지와 무관하게 **Hermes 프로그램
전체를 통틀어 한 곳**에 쌓인다. 두 층이 나뉘는 기준이 서로 다르다는 게 이번에 확인한 사실이다.

## 8. 프로파일(profile) — 사람별로 학습 기억을 나누는 실제 방법

7번에서 확인한 문제("학습 기억은 Hermes 프로그램 전체에 한 곳만 있다")를 풀 수 있는
유일한 방법이 Hermes 안에 이미 있다 — **프로파일(profile)**이라는 기능이다. 이걸 실제로
어떻게 쓰는지 코드 레벨로 확인했다.

### 프로파일은 그냥 폴더 하나다

프로파일은 특별한 개념이 아니라, `~/.hermes/profiles/이름/`처럼 **자기만의 설정 파일,
`.env`(비밀값), 학습 기억 파일(MEMORY.md/USER.md), 대화 기록 저장소를 통째로 담은
폴더 하나**다. 아무 이름도 안 정하면 쓰는 기본 폴더(`~/.hermes` 자체)도 사실 "default"라는
이름의 프로파일 취급을 받는다. 즉 프로파일 하나 = 독립된 미니 Hermes 설치본 하나라고
이해하면 된다.

`multiplex_profiles: true`라는 설정을 기본 프로파일의 설정 파일에 켜두면, **Hermes
프로그램 하나가 여러 프로파일(폴더)을 동시에 서비스**할 수 있게 된다.

### 방법 A — 프로파일마다 메신저 로그인 정보(토큰)를 따로 발급

여기서 중요한 제약을 하나 확인했다: Mattermost처럼 "연결을 계속 열어두는" 방식의
메신저는, **프로파일마다 서로 다른 봇 계정(토큰)을 요구**한다. 두 프로파일이 같은
Mattermost 토큰을 쓰려고 하면, Hermes가 시작할 때 이걸 감지해서(토큰 값을 해시로
비교하는 방식) "이 프로파일은 이미 다른 프로파일이 쓰고 있는 자격 증명이라 시작 안
시킴"이라고 로그를 남기고, **그 프로파일의 연결만 조용히 빼고 나머지는 정상적으로
돌아간다** (전체가 멈추지는 않음).

그리고 각 프로파일의 설정 파일 안에서 Mattermost 접속 정보를 적는 항목 이름
(`MATTERMOST_URL`, `MATTERMOST_TOKEN` 등)은 프로파일마다 다른 이름을 쓰는 게 아니라
**모든 프로파일이 똑같은 이름을 쓰되, 각자 폴더 안의 값만 다르게 넣는** 방식이다.
즉 "여운호 폴더 안의 `MATTERMOST_TOKEN`"과 "김동연 폴더 안의 `MATTERMOST_TOKEN`"이
서로 다른 값을 갖는 식으로 구분된다.

정리하면: **"팀원 수만큼 Mattermost 봇 계정을 따로 만들고, 그 계정들을 각자 다른
프로파일 폴더에 하나씩 배정"**하는 것이 지금 Hermes 코드가 지원하는 방식이다. 이렇게
연결된 프로파일들은 전부 **하나의 Hermes 프로세스, 하나의 프로그램 실행 안에서** 동시에
돌아간다(프로파일마다 별도 프로그램을 띄우는 게 아니라, 한 프로그램 안에 연결 여러
개를 열어두는 방식) — 그래서 팀원이 늘어나도 서버 자원을 크게 더 쓰지는 않지만, 연결
개수가 아주 많아지면(수십~수백 명 단위) 그만큼 한 프로그램이 감당해야 할 부담이 는다는
점은 고려할 만하다.

### 방법 B — 봇 계정 하나로 통일하고, 보낸 사람을 보고 자동으로 프로파일을 고르기

Hermes 코드 안에는 "메시지가 들어왔을 때 이걸 처리하는 함수를 내가 원하는 걸로
바꿔치기할 수 있는" 확장 지점이 있다(`메시지 핸들러 등록`이라는 기능). 그리고 이
핸들러가 "메시지를 어느 프로파일로 보낼지" 자동으로 정해주는 기본 로직은, **"이미
정해진 프로파일이 없을 때만" 기본값을 채워 넣는 방식**으로 되어 있다는 걸 확인했다.

즉 이 확장 지점에 우리 코드를 살짝 끼워 넣어서, "이 메시지를 보낸 사람의 Mattermost
사용자 ID(이름이 아니라 계정마다 고유하게 부여되는 진짜 식별값)를 보고, 그에 맞는
프로파일을 우리가 직접 정해주는" 로직을 추가하면, **봇 계정은 팀 전체에 딱 하나만
있어도 사람별로 학습 기억이 나뉘게 만들 수 있다.** 다만 이 확장 지점은 공식적으로
"이렇게 써도 된다"고 문서화된 기능이 아니라, 코드 구조상 가능하다는 걸 직접 확인한
수준이다 — 이걸 활용하는 코드는 실제로 Hermes 프로세스 코드 로딩 방식 안에서(플러그인
형태로) 실행되어야 동작한다.

### 방법 A/B 공통점 — 둘 다 "구별 로직"이 Hermes 프로세스 안에 있다

방법 A는 코드를 안 짜도 되고, 방법 B는 코드를 짜야 한다는 차이가 있지만, **"누구를
어디로 보낼지 정하는 로직 자체는 결국 둘 다 Hermes 프로세스 안에서 일어난다.** 방법
A는 "어느 봇 계정(연결)으로 메시지가 왔는지"만 보고 자동으로 나누는, **Hermes에
원래부터 내장된 유일한 구별 방식**이고, 방법 B는 그 위에 우리가 코드를 얹어서 "누가
보냈는지"까지 보게 만드는 확장이다. Hermes 자체에는 "발신자가 누구인지"를 구별하는
기능이 원래 없다 — 프로파일 구별은 순전히 "어느 연결로 메시지가 왔는가"로만 이루어진다.

### 외부 API 창구(api_server)로는 이 문제를 못 피해간다 — 확인 결과 정정

처음에는 "그럼 3번 항목에서 확인한 외부 HTTP 창구(`api_server.py`)를 쓰면, 굳이 Hermes
안에 코드를 안 얹어도 요청 주소만 사람마다 다르게 보내서(`/p/여운호/...`,
`/p/김동연/...`) 프로파일을 구별할 수 있지 않을까" 하고 예상했다. `webhook`이라는
다른 종류의 창구에는 실제로 이런 "주소에 이름을 붙여서 사람을 구별하는" 기능이
있어서, 같은 방식이 `api_server`에도 있을 거라 짐작한 것이다.

코드를 직접 확인해보니 **이 예상은 틀렸다.** `api_server`는 Hermes 프로그램을 켤 때
"나는 이 프로파일(폴더) 하나만 쓸게"라고 이미 고정된 상태로 열리는 창구다. 그 창구
주소로 아무리 다른 이름을 붙여서 요청을 보내도, **그 창구 자체가 처음부터 특정
프로파일 하나에 묶여서 열려 있기 때문에, 결국 그 프로파일로만 처리된다.** 요청 주소로
사람을 구별해서 다른 프로파일로 나눠주는 기능은 `webhook`에만 구현되어 있고,
`api_server`에는 없다는 게 소스 코드로 확인된 사실이다. 즉 외부 API 창구를 쓴다고
해도, Hermes 프로세스 하나로는 여전히 "한 프로세스 = 한 사람"이라는 제약을 벗어날
수 없다.

### 방법 D — Hermes를 아예 사람 수만큼 여러 벌 띄우고, 구별은 전부 우리 레이어에서

앞의 세 가지를 종합하면, "Hermes 코드/설정을 하나도 안 건드리면서, 사람을 구별하는
로직을 전부 우리 쪽 레이어에만 두고 싶다"는 목표를 이루는 방법은 하나 남는다 —
**"프로파일"이라는 한 프로세스 안에서 여러 사람을 나누는 기능 자체를 아예 안 쓰고,
Hermes를 사람 수만큼 완전히 별개의 프로그램으로 여러 벌 띄우는 것**이다.

- 팀원 한 명당 완전히 독립된 Hermes 프로그램 한 벌 (각자 자기만의 폴더, 학습 기억,
  api_server 창구를 가짐 — 예: 여운호용은 8001번 문, 김동연용은 8002번 문)
- 각 Hermes는 **코드도 설정 방식도 순정 그대로**다. "프로파일 다중 서비스" 기능조차
  쓸 필요가 없다 — 그냥 사람 수만큼 복사해서 각자 다른 포트에 띄우는 것뿐이다.
- 우리 레이어가 Mattermost에 봇 계정 **하나**로 연결해서 모든 메시지를 받고, 메시지
  보낸 사람의 Mattermost 계정 ID를 확인해서(이 매칭표는 우리가 직접 관리) "이 사람은
  8001번 문으로" 하고 그 사람 전용 Hermes의 api_server에 요청을 보낸다.

이 방식은 "발신자를 구별하는 로직"이 정말로 100% 우리 레이어 안에만 있고, Hermes
프로세스 안에는 그런 로직이 전혀 없다는 점에서 방법 A/B와 근본적으로 다르다. 대신
치러야 하는 대가는, Hermes 프로세스가 **팀원 수만큼 통째로 늘어난다**는 것이다 — 이
자원 사용 문제는 팀 규모가 커질수록 별도로 검토가 필요한 부분이다.

### 정리 — 네 가지의 차이

| | 방법 A: 봇 계정을 팀원 수만큼 | 방법 B: 봇 계정 하나 + 코드 확장 | 외부 API 창구(단독) | **방법 D: Hermes를 사람 수만큼** |
|---|---|---|---|---|
| 되는가 | 됨 | 됨(코드 필요) | **안 됨** (한 프로세스=한 프로파일 고정) | 됨 |
| 구별 로직 위치 | Hermes 프로세스 안(기본) | Hermes 프로세스 안(확장) | 해당 없음 | **전부 우리 레이어 안** |
| Hermes 코드/설정 변경 | 설정만 | 코드 추가 | 없음 | **없음(완전 순정)** |
| 자원 사용 | 프로세스 1개, 연결 여럿 | 프로세스 1개 | 프로세스 1개(=1명분) | **프로세스 N개(사람 수만큼)** |

## 9. 종합 — TeamBrain 설계에 주는 의미

- Hermes가 이미 갖고 있는 것(메신저 연결, 개인별 기억, 대화 검색, 스킬 자동 생성)은 그대로
  가져다 쓸 수 있어서, 이 부분을 처음부터 새로 만들 필요는 없어 보인다.
- 다만 Hermes의 기본 구조는 "대화방+사람" 단위로 기억을 잘게 쪼개놓기 때문에, 여러 팀원의
  개인 기억을 팀 전체가 공유하는 지식으로 엮는 작업은 Hermes 안에 없는 완전히 새로운 레이어다
  — 이게 우리 프로젝트에서 우리가 직접 설계하고 만들어야 하는 핵심 novel 부분이다.
- 이 새 레이어를 만들 때, Hermes를 고치거나 그 안에 끼워 넣지 않고, 완전히 독립된 프로그램이
  Hermes의 공식 외부 API 창구(`api_server.py`)를 통해 필요한 정보를 주고받는 방식이 라이선스
  규칙을 지키면서 구현할 수 있는 가장 깔끔한 방법으로 보인다.
- 단체 채팅방에서 "봇을 부르기 전 대화 맥락을 자동으로 챙겨주는" 기능은 우리가 쓸 메신저
  환경에는 기본으로 들어있지 않으므로, 필요하다면 새 레이어 쪽에서 직접 구현해야 한다.
