"프로파일 만드는 것"은 이전에 팀원별 "진짜 개인 에이전트"를 만들 때 조사했던 그 기능입니다. 정리하면:

## Hermes profile이란

`~/.hermes/profiles/<이름>/`에 **완전히 독립된 HERMES_HOME**을 만드는 겁니다. 그 안에 `SOUL.md`(자기모델), skills, 기억, config가 전부 별도로 있어서 — 봇 하나가 그냥 "대화 상대별로 기억만 나눠 갖는" 게 아니라, **정말로 서로 다른 별개의 에이전트**가 됩니다.

## 왜 필요했었는지 (배경)

전에 확인했던 것처럼, Hermes의 기본 세션 격리(`group_sessions_per_user`)는 **대화 기억만** 사람별로 나눠줄 뿐, SOUL.md·skills·config는 한 프로세스 안에서 다 공유됩니다 — "같은 뇌, 노트만 따로"인 상태. 기획서의 "주요 기능3 — 개인 학습 에이전트"(각자 업무 스타일에 맞춰 스스로 발전하는 개인 에이전트)를 실제로 구현하려면 이 profile이 필요했습니다.

## 만드는 방법 2가지

**방법 A — 프로세스 여러 개 (기본, 우리가 채택한 방식)**
```bash
hermes profile create <이름>
hermes profile setup <이름>
hermes profile gateway install <이름>
hermes profile gateway start <이름>
```
사람마다 완전히 독립된 프로세스라 격리는 확실하지만, 사람이 늘수록 서버 자원(프로세스 수)이 그만큼 늘어남.

**방법 B — 멀티플렉싱** (`hermes config set gateway.multiplex_profiles true`)
프로세스 하나가 여러 profile의 어댑터를 같이 띄우는 방식. 자원은 아끼지만, 확인해본 결과 `MATTERMOST_ALLOWED_USERS` 같은 사용자별 접근 제한이 **profile별로 안 먹히는 버그**가 있어서(`authz_mixin.py`가 profile별 시크릿 스코프를 못 읽음), 우리 팀은 이걸 피하고 **방법 A**로 가기로 했었습니다.

지금 만들고 있는 `mattermost-search-mcp`와는 별개 층입니다 — profile은 "팀원 개인별 Hermes 인스턴스를 어떻게 나눌지"의 문제고, MCP 서버는 "봇 하나가 Mattermost 데이터를 어떻게 조회할지"의 문제라, 서로 독립적으로 진행하시면 됩니다.
